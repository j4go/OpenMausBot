# 产品开发工作流

## 使用门禁

仅当用户明确要求使用 product-development-workflow skill，或明确点名 `superpowers:product-development-workflow` 时使用。

不要因为一般性的规划、设计、原型或开发请求而自动触发本 skill。

## 中文回复和中文产物契约

执行本 skill 时，默认使用简体中文回复用户，并默认使用简体中文编写所有产品工作流交付物，包括问题澄清、PRD、原型页面文案、测试用例、技术方案、开发计划、评审门禁、状态说明和最终评审说明。现场产品工作流用 `product-workflow`；看板落在 `.review-board/`，不要手写 tab 正文。

命令名、文件路径、API 路由、代码标识符、枚举值、测试编号、验收标准编号保留原始技术形式。只有用户明确要求其他语言时，才使用其他语言。

## 硬门禁

以下产物全部写入并获得用户明确批准前，不得开始实现：

- PRD
- 原型产物，或用户明确确认原型不适用
- 测试用例
- 技术方案
- 开发计划

批准必须明确。如果任何产物缺失、仍是草稿、未确认不适用或等待评审，继续工作流产物生成/评审，不要进入实现。

## 输入契约

写任何产物前，先把用户需求规范化为问题表格，包含：

- 原始需求、目标用户、业务背景、当前流程、触发场景、约束、假设、成功指标、风险、待确认问题。
- 使用的证据：仓库上下文、提供的链接/文档、当前产品行为，或明确标记的假设。
- 既有产物状态：`Not generated`、`Draft`、`Reviewed`、`Approved` 或 `Not applicable`。

如果输入缺少领域、目标用户、触发场景或成功指标，先问一个澄清问题，再生成 PRD。不要把缺失信息写成确定事实；必须标为假设和待确认问题。

每个后续阶段都必须先读取输出目录中的既有产物。如果必需前序产物缺失或未批准，先请求评审，不要跳步。

## AI 不确定性澄清门禁

写任何正式产物前，先判断哪些内容是 AI 无法从用户输入、既有产物或项目上下文中可靠确认的。阻断性不确定项不得只写进“假设”或“待确认问题”后继续生成完整产物，必须先问用户。

阻断性不确定项包括会改变以下内容的未知信息：

- 目标用户、业务目标、成功指标、范围边界或非目标
- 核心用户旅程、触发场景、验收标准或优先级
- 权限、安全、隐私、合规、数据保留或审计要求
- 系统边界、集成方、数据模型、状态机、接口契约或发布/回滚策略
- 项目事实与用户表述、既有产物或代码探索结果冲突

如果存在阻断性不确定项，一次只问当前阶段继续所需的最少必要问题，优先问会影响最大范围决策的问题。只有用户明确回答，或明确授权“先按假设继续”，才能继续生成完整产物。非阻断性不确定项可以标为假设或待确认问题，但产物必须说明这些假设不影响当前阶段评审。

## 反薄产物门禁

薄摘要是失败产物。不要产出占位、只有大纲或“仅演示”的产物。每个产物都必须详细到产品、设计、QA 或工程评审人可以直接做决策，而不需要要求“展开一下”。

如果输入很弱，导致产物可能偏短，先澄清；如果仍需继续，必须明确未知项，并围绕已知上下文提供完整草稿。

每个产物开头必须提供足够上下文，帮助第一次阅读的人理解：这个阶段为什么存在、谁应该评审、评审人需要做什么决策、依赖哪些前置事实或假设、关键术语/编号/角色/状态是什么意思、哪些内容尚未确认。不要让产物一开始就进入表格、编号或接口细节。

## 输出目录

在以下目录创建产物：

```text
docs/product-development/YYYY-MM-DD-<topic>/
```

必需文件：

- `prd.md`
- `prototype.html`
- `test-cases.md`
- `technical-solution.md`
- `development-plan.md`
- `index.html`

## 工作流

1. 创建输出目录并初始化 `index.html`。
2. 写 `prd.md`，并更新 `index.html` 的 PRD tab，状态为 `Draft`。
3. 请求用户评审 PRD。批准后把 PRD tab 状态更新为 `Approved`。
4. 与用户确认视觉原型是否有用。始终创建 `prototype.html`。如果视觉原型有用，做成自包含原型并更新 Prototype tab 为 `Draft`；如果不适用，`prototype.html` 必须解释原因并提供等价评审产物。
5. 请求用户评审 `prototype.html`。批准后更新 Prototype tab 为 `Approved`；若不适用，用户确认后更新为 `Not applicable`。
6. 写 `test-cases.md`，并更新 Test Cases tab 为 `Draft`。
7. 请求用户评审测试用例。批准后更新 Test Cases tab 为 `Approved`。
8. 写 `technical-solution.md`，并更新 Technical Solution tab 为 `Draft`。
9. 请求用户评审技术方案。批准后更新 Technical Solution tab 为 `Approved`。
10. 写 `development-plan.md`，并更新 Development Plan tab 为 `Draft`。
11. 请求用户评审开发计划。批准后更新 Development Plan tab 为 `Approved`。
12. 所有产物批准或明确确认不适用后，运行开工门禁：检查工作树、任务独立性、文件 ownership、TDD 检查点和验证命令，并向用户推荐 `single` 或 `multi-subagent` 执行方式。
13. 用户明确批准执行方式后，才进入开发执行。

每次更新一个产物后，只改当前 tab 的内容和状态，保留其他 tab 内容；但 `<title>`、顶部标题、当前阶段提示、导航状态和 hash/tab 激活脚本属于全局看板元信息，必须随当前阶段同步更新。

## 软件门户

同步时机见 `product-workflow/references/common-contracts.md` § 软件门户同步。命令见 `docs/product-workflow/portal.md`。

## `index.html` 契约

`index.html` 必须自包含：HTML、CSS、JavaScript 都内联，不依赖外部脚本、样式、字体或网络资源。

必须包含以下 tab：

- 问题澄清
- PRD
- 原型
- 测试用例
- 技术方案
- 开发计划
- 开工
- 开发执行

每个 tab 必须且只能显示以下状态之一：

- `Not generated`
- `Draft`
- `Reviewed`
- `Approved`
- `Not applicable`

未生成的产物初始化为 `Not generated`。更新某个 tab 时，保留其他 tab 既有内容。

每个 tab 必须包含可评审的产物内容，不能只有链接或两句话摘要。长表格可以为了阅读性压缩，但必须保留决策、风险、验收标准、测试覆盖、接口、任务顺序和审批状态。

## 双视图评审契约

`index.html` 的每个阶段 tab 必须包含两个视图：

- 人类评审视图：默认展示，强调可读、可理解、可评审。包含评审重点、关键结论、图示、风险/门禁、评审锚点，避免把完整 Markdown 长文直接堆给人。
- AI Markdown 视图：用于后续 AI/agent 继续处理，强调完整、可复制、可追踪。保留对应产物的 Markdown 源内容或等价结构化源内容，尽量不丢编号、表格、接口、测试用例和命令。

两个视图必须在同一个 tab 内切换，不能让评审人跳到另一个文件才能完成阅读。默认打开人类评审视图。

人类评审视图顶部必须有“阅读上下文”区，说明该 tab 的目的、适合谁评审、评审时要判断什么、读之前应该知道什么。

人类评审视图中的每个 section 都必须转成可视化评审组件，而不是直接堆 Markdown。组件选择规则：

- 背景、目标、范围、非目标：用上下文面板、范围卡片或决策卡表达。
- 用户画像、角色、模块、里程碑、任务：用分组卡片表达，突出目标、痛点、职责、退出证据。
- 用户旅程、流程、状态、架构、发布路径：用流程图、状态图、阶段流或 Mermaid 语义的等价 HTML/SVG 表达。
- 用户故事、验收标准、测试用例、追踪矩阵：用可切换 tab、检查清单、追踪卡表达，按角色、旅程、优先级、AC 或里程碑分组；分组必须服务阅读效率，不能为了“可切换”而切得过细。
- 风险、待确认问题、错误处理、权限、回滚：用风险/决策面板表达，显式展示影响、判断条件、负责人或下一步动作。

Markdown 表格在人类视图中不能作为主要表达。必须转换成移动端可读的 tab + 卡片、矩阵卡、检查列表或对比面板；完整原表格保留在 AI Markdown 视图。

tab 和平铺的选择规则：

- 分组数不超过 6 且每组平均超过 1 条时，可以使用 tab，例如测试用例按 P0/P1/P2、追踪矩阵按旅程。
- 分组数超过 6，或多数分组只有 1 条时，优先平铺为卡片网格，例如 AC 清单、指标、权限、备选方案。
- 平铺优先采用“纵向表格模式”：一行一个评审项，左侧展示分组/编号，右侧按字段展示内容；移动端可退化为单列字段块。只有画像、摘要、页面状态这类非表格信息才使用多列卡片。
- 不允许把 8 个以上的一条目分组做成一排小 tab 让评审人逐个点击。

## H5 图示契约

`index.html` 和 `prototype.html` 这类 H5/HTML 产物中，凡是流程、状态机、系统架构、角色协作、依赖关系、验收标准到测试用例的追踪关系，仅靠文字或表格不够清楚时，必须画成图。

- 优先使用 Mermaid 语义来组织图，例如 flowchart、sequenceDiagram、stateDiagram、journey、mindmap。
- 如果 HTML 要求自包含，不依赖外部 CDN 或运行时 Mermaid，也必须优先在生成阶段把标准 Mermaid 源码预渲染成内联 SVG。只有 Mermaid 渲染失败时，才降级为 HTML/CSS 图或源码提示；不要只放一段 Mermaid 源码让评审人自己想象。
- 图旁边保留简短中文说明，说明这张图帮助评审什么决策。
- 技术 token、接口名、状态名可以保留原始形式，但图中的说明文案默认中文。

## 质量标准

### 问题澄清

- 包含目标用户、用户任务、当前流程、痛点、业务目标、约束、假设、风险、成功指标、非目标、待确认问题。
- 至少 3 个具体触发场景，除非功能确实只有单场景。
- 区分已确认事实和假设。

### PRD

- 包含用户问题、目标用户、目标、非目标、范围、约束、假设、风险、成功指标。
- 包含核心用户旅程和验收标准。
- 区分事实和待确认问题。
- 具体到设计、测试、实现可以继续推进，不需要猜。
- 普通产品需求至少 5 条用户故事和 8 条验收标准。若确实更少，必须说明原因。
- 每条验收标准必须关联用户故事或可衡量结果。
- 用户旅程、用户故事、验收标准必须建立同一套追踪关系，PRD 中必须包含“旅程 → 用户故事 → 验收标准”矩阵，确保每个核心旅程都有故事和 AC 覆盖。
- 涉及多角色交互或状态变化时，PRD 必须补充时序图和状态机图，帮助评审交互顺序和关键状态边界。

### 原型

- `prototype.html` 必须自包含、独立、可交互，首屏直接呈现产品界面或工作台。
- UI 类需求必须包含代表性页面、主流程、空/加载/错误/成功等可切换状态、真实操作控件和响应式体验。
- `prototype.html` 不得混入大段 PRD 背景、用户故事、验收标准、技术方案或测试用例；这些评审上下文放在 `index.html` 的 Prototype tab。
- 非 UI 类需求必须提供自包含的交互式等价原型，例如流程模拟器、状态机沙盒、CLI/API 控制台或数据流演示；只有用户明确确认不适用时，才允许非交互评审产物。

### 测试用例

- 覆盖主流程、边界、错误状态、权限、数据边界、回归风险。
- 用例必须追踪到 PRD 验收标准。
- 指定准备、操作、期望结果、优先级。
- 说明人工和自动化覆盖建议。
- 普通产品需求至少 20 条 P0/P1/P2 用例，除非范围明确更小。

### 技术方案

- 描述架构、涉及模块、数据模型或 API 变化、ER 图、API 汇总表、依赖、迁移、发布策略、可观测性。
- 解释关键取舍和备选方案。
- 说明安全、隐私、性能、可靠性、兼容性影响。
- 具体到工程师可实现，不需要重新发现方案。
- 包含接口字段、状态流转、错误处理、鉴权/权限影响、回滚行为。
- 检查单元测试基建现状：测试框架、测试命令、JUnit XML/覆盖率 XML 报告产物；若缺失，标记需要 `product-unit-test-init` 在开工前准备。
- 检查 Git Hook 质量门禁现状：当前 hook manager、hook stages、质量命令覆盖、多技术栈子项目覆盖；若缺失或不可验证，标记需要 `product-git-hook-init` 在开工前准备。

### 开发计划

- 拆成有序、可验证任务。
- 包含测试先行检查点、验证命令、评审点、回滚考虑。
- 每个任务足够小，可独立实现和评审。
- 标明依赖、顺序约束、不可并行任务。
- 代码库可访问时，包含具体文件/模块范围。
- 包含命令级验证和期望证据。
- 若技术方案标记测试基建缺口，必须把 `product-unit-test-init` 准备任务列为第一个前置任务，完成前不得进入实现。
- 若技术方案标记 Git Hook 质量门禁缺口，必须把 `product-git-hook-init` 准备任务列为第一个开工前置任务之一，完成前不得进入实现；若同时存在测试基建缺口，必须显式排序两个前置任务。

### 开工

- 检查所有前置产物已批准或明确不适用。
- 检查开发计划任务是否能映射到测试用例，并具备 TDD 检查点。
- 检查单元测试基建前置任务是否已经完成；未完成时先触发 `product-unit-test-init` 并等待用户手动验证。
- 检查 Git Hook 质量门禁前置任务是否已经完成；未完成时先触发 `product-git-hook-init` 并等待验证结果。
- 检查当前工作树和分支风险，保护用户无关改动。
- 根据任务数量、写入范围、依赖关系和 subagent 可用性，推荐 `single` 或 `multi-subagent`。
- 多 subagent 仅在用户明确批准后使用；无论哪种方式都必须先写失败测试，再实现。

## 输出自检

请求用户评审任何产物前：

1. 占位符扫描：移除 `TBD`、`TODO`、“稍后补充”、模糊 bullet、空章节。
2. 薄产物扫描：确认产物达到质量标准，不只是摘要。
3. 追踪扫描：PRD 验收标准映射测试用例；测试用例映射技术风险；开发任务映射技术方案。
4. Tab 同步扫描：`index.html` 状态和 tab 内容与刚写入的产物一致，且没有覆盖其他 tab。

## 完成消息

所有产物写入并批准后，用中文回复：

```text
产物已准备好：docs/product-development/YYYY-MM-DD-<topic>/index.html。请在实现前进行最终评审。
```
