## 二、场景 → skill → 角色 决策表（机制对齐）

> 与第一节映射互补：第一节是"角色能调什么"（备而不用），本节是"什么场景必调什么"（指名纪律）。
> 两个背景事实：① Matt 核心流程 skill（grill-me / to-spec / to-tickets / wayfinder 等）多为 `disable-model-invocation: true`（等人显式点名，模型不能自动想起就调）——解法不是改 Matt 技能库（不侵入第三方），而是指挥官在**委派指令中显式指名**（显式指名调用不受该标志限制）；② 各角色 bot 实际是否调用 skill 无法从外部看到（那是会话内部），只能靠委派指令指名 + 产物标注**间接闭环**。

| 触发场景 | 指挥官动作 | 指名 skill | 执行角色 | 产物 / 痕迹 |
|---|---|---|---|---|
| 需求模糊 / 高风险 / 改动大 | 逐步追问需求方（对抗质询） | `grill-me`（= grilling 组合壳） | 指挥官本人 | clarify.md §3 假设清单 |
| 需求清楚，要成文 | 委派规格（指名调用） | `to-spec` | Spec | prd.md（header 标注"由 to-spec 产出"） |
| 规格 / 计划要拆分 | 委派计划（指名调用） | `to-tickets` | Tickets | development-plan.md |
| bug / 异常报告 | 委派诊断（指名调用） | `diagnosing-bugs` | QA / Implement | 根因分析 + 修复单测 |
| 超大任务 / 方向不明 | 委派探路（指名调用） | `wayfinder` | 指挥官 + Spec | 方向结论 → 定 L/M |
| 需求清楚且 S 级 | 直接委派快速验证 | `tdd` / `implement` | Implement | 最小产物 + 验证证据 |

### 委派契约（指挥官执行，可审计）

1. 委派指令写死 skill 名："用 `to-spec` 产出 prd.md"，不写笼统的"写个规格"；
2. 切片产物 header 标注来源 skill（`to-spec` / `to-tickets` 等自带调用痕迹）；
3. 显式指名即绕过 `disable-model-invocation`，无需修改 Matt 技能库；
4. **HITL 上抛契约**：子 bot 调 Matt skill 遇到 HITL 步骤（`to-spec` 的 check seams、`to-tickets` 的 quiz、grilling 的对抗质询等），一律把问题**原样上抛指挥官**，指挥官转问需求方、拿到答复再回传；**禁止子 bot 自答或替需求方拍板**。背景：Matt skill 是「agent 直接对用户」骨架（人是技能内对话对象），我们是「指挥官代理需求方、子 bot 只干活」骨架，子 bot 没有对需求方的直接通道。
5. **与需求方交互约定（用户裁定 v2）**：审批/决策类请求**优先用问题卡片（ask_user_question）直接询问**，选项仅「同意 / 拒绝」二选一，需求方回答**回传会话**、收到答复后继续——交互无断层；**非必要不发 OMB native-approval 审批弹窗**（实测缺陷：用户点击「允许」后 decisions.ndjson 已记录 user-approved，但结果**不回传 agent 会话**，曾出现审批被误判为未批/跳过）；需要需求方手动补充信息时，先问「是否愿意填写」二选一，同意后由需求方在**聊天输入框自行补充回答**，bot 不在弹窗/问题卡片中要求填写任何内容。例外：SOUL / 团队配置类变更只能走平台确认卡（propose_profile / propose_team_setup），不属于日常审批弹窗。全组生效：各角色 SOUL 内置条款 + Section Context 注入（粘贴区第五节）。
