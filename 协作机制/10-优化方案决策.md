## 二、逐项决策详情

### 1. 度量闭环 —— 补，轻量版（每切片 3 个数）

**决策**：不硬套 DORA 四指标（团队级长期数据，单机单人项目会变填表负担），改为每切片在 `.workflow-state.json` 记录 3 个数：

| 度量 | 含义 | 记录时机 |
|---|---|---|
| 前置时间 | 澄清 → Reviewed 的耗时 | Reviewed 写入时记 |
| 缺陷返工数 | 实现 → QA 通过期间的缺陷返工次数 | QA 判定时记 |
| QA 一次通过 | QA 是否一次通过（是/否） | QA 判定时记 |

**理由**：三个数即可撑起对账闭环的量化部分，成本几乎为零；定性流程对账（04-约束链与对账.md）保留，度量是它的量化补充。
**落地**：01-需求分级.md 新增约定——`.workflow-state.json` 增加度量字段；QA 环节与 Reviewed 环节写入。

### 2. CI —— 定义为"CI 等价门禁"，不假装有 CI

**决策**：单机环境没有 push 即 CI 的客观条件，不引入伪 CI。但"commit 后无人自动验证"的缺口真实存在，用现有机制补上并**正名**：

> **代码审查通过 → 构建验证，是 Reviewed 之后、QA 之前的固定闸（"CI 等价门禁"）。**

**理由**：这个顺序当前已被状态机锁死，机制已存在，缺的只是显式命名与文档化。
**落地**：01-需求分级.md 原则 8 将构建验证步骤标注为"CI 等价门禁（固定闸）"。

### 3. 分支/PR —— 显式声明为有意选择，不引入

**决策**：保持直接 commit 主分支 + 流程内双审查（对抗审查 + 代码审查），不引入短命分支/PR。

**理由**：单人 + 单机场景下，短命分支是纯负担；流程内双审查已覆盖 PR 的核心价值（独立评审）。此决策写入文档作为**可审计的选择**，并记录触发变更条件。
**触发变更条件**：进入多人协作 / 多机协作时，重开此决策。
**落地**：01-需求分级.md 新增决策记录条目（原则 10）。

### 4. 测试覆盖率门禁 —— 补，按风险分级

**决策**：不搞一刀切 80%，按风险分级：

| 模块类别 | 覆盖率要求 |
|---|---|
| 核心业务模块（后端服务层等） | ≥ 80% |
| 工具 / 脚本 / 演示页 | 不设阈值 |

**理由**：TDD 保证"有测试"，阈值保证"测到关键处"，是两个不同问题；后者目前无人管。风险分级避免把低风险代码拖进高成本。
**落地**：01-需求分级.md 原则 9 补充覆盖率分级约定。

### 5. TDD 在 S 级 —— 保持强制，不开口子

**决策**：S 级同样执行 TDD，不设"test-after 但必须补测试"的口子。

**理由（需求方裁定原话）**："S 级别的 tdd 就足够了，不用那么测试；如果需要比较严谨的测试，就不应该归类为 S 级。"
**推论**：分级本身承担风险裁剪——需要严谨测试的需求，按定义应归 M/L 级，而不是在 S 级放松测试要求。
**落地**：01-需求分级.md 原则 11 补充此裁定说明。

### 6. 更严项 6 条 —— 全部保留

对抗审查（fresh 上下文三轴）/ QA 独立门禁 S 级不豁免 / 状态机锁步 / TDD 强制 / Reviewed 唯一写入者 / 部署默认 dry-run——**全部保留，不动**。

**理由**：生产级裁定下"流程重量是交付物"；这 6 条是这套流程区别于普通团队的核心，动了就失去演练意义。

### 7. 度量复盘机制（v2.1 补充）

**背景**：决策 1 落地时只定义了「每切片记 3 个数」，未定义「记了怎么用」——首个完成切片走完 8/8 流水线但 `metrics` 字段为空，暴露定义与执行脱节（无记数责任人、无聚合点、无复盘节奏）。

**决策**：补上「用数」环节，与 04-约束链与对账.md 定性对账闭环合并为三段闭环：

| 环节 | 定义 |
|---|---|
| 聚合点 | `协作机制/11-度量台账.md`——每切片一行（需求 / lane / 三数 / 备注） |
| 记录责任 | 指挥官：Reviewed 写入时记 `lead_time_to_reviewed`；收到 QA 判定后 24h 内补记另两数（QA 是只读 bot 不写状态机） |
| 复盘节奏 | 切片级即时记数 + 每 3~5 个切片或每月一次复盘（指挥官主持、与需求方对齐，文档型任务不广播） |
| 阈值信号 | M/L 级 `lead_time_to_reviewed` > 3 天须写原因；`rework_count ≥ 2` 须写根因；`qa_first_pass = false` 必须写缺陷摘要 |
| 复盘产出 | 保留 / 调整 / 废弃某机制 → 写进本文件 → 决策表（02-场景决策表.md）据此刻意修订 |

**落地**：01-需求分级.md 新增原则 12；新建 11-度量台账.md（含首个切片补记与复盘记录 1：lead_time 因缺起点时间戳标数据缺失）。

### 8. 能力边界文档化 + Section Context 公共规则落地（v2.2 补充）

**背景**：需求方裁定「灵活分解需求、每个 agent 接收任务干活，但**不是所有的活都可以做**」。能力边界此前散落在各 SOUL 与 03-工作流与产物.md 直视图（按阶段聚合），缺一张按角色聚合的集中矩阵：从任意入口进来的任务，接单 bot 能不能接取决于自己 SOUL 写得清不清楚；需求方也没有一处能看到「谁绝对不能做什么」。

**决策**：

1. **05-能力边界矩阵.md 建立**：全局禁做清单（G1–G8）+ 8 角色 × 可写范围 × 绝对禁做 矩阵 + 裁决优先级（用户当前指令 > Section Context > SOUL > 机制清单）。
2. **Section Context 公共规则落地并生效**：OMB 官方分区级共享指令（源码 `server/section-context.ts`），内容每轮注入本分区所有 bot 的 prompt；只有用户能写、agent 显式禁写；v1 内容 = 入口归一 + 四条铁律 + 事实源指针 + 协作姿态，留档于 `协作机制/section-context.md`。
3. **多入口归一四层设计正式生效**：规则层（Section Context + SOUL 入口条款）→ 入口层（业务需求一律上报指挥官、只读咨询直接答）→ 状态层（切片 + 状态机唯一事实源）→ 验证层（QA / Reviewed 门禁不可豁免）。
4. **知识沉淀**：项目学习笔记新增 Section Context 机制 + 多入口归一 + 能力边界相关笔记（见初始化包教程平台事实）。

**诚实边界**：OMB 无跨 bot 共享记忆，四层围堵只能降低漂移、让偏差可审计，不能保证趋同（模型概率本质，04-约束链与对账.md 三条诚实边界）；「构造性趋同」只有单 agent 架构才能给，本方案是「多脑 + 外部共识文件」的工程化近似。

### 9. 环节时间线记录（v2.3 补充）

**背景**：决策 1/7 落地后，`lead_time_to_reviewed` 只有「澄清→Reviewed」总时长，无法复盘单个环节（规格、计划、实现、审查、构建、QA 各自耗时）——需求方提出「每个需求从确定开始到最终确认，要有时间线与各环节耗时记录，方便日后复盘」。

**决策**：

1. `.workflow-state.json` 顶层新增 `timeline` 数组（每环节：stage / started_at / ended_at / duration / note），作为环节时间线的唯一事实源。
2. **实时记录纪律**：指挥官（唯一写入者）在委派发出时记 `started_at`，阶段状态写入时记 `ended_at` + `duration`；不事后补、不可回溯标 `null` 并注明原因。
3. 度量台账表头新增「环节耗时」列（聚合引用 timeline）。

**首例教训**：首个切片 clarify~对抗审查阶段未实时记起点，补记时仅可考若干离散节点，中间环节耗时不可回溯；QA 判定时间戳与构建收尾存在跨 bot 时钟/写入时序差异，已如实标注。
**落地**：01-需求分级.md 新增原则 13；首个切片状态机补 `timeline`；11-度量台账.md 扩展列。

## 四、迁移真实项目时的裁剪声明

本方案所有"补"与"保留"均基于"项目 = 流程演练项目，流程重量是交付物"的定位（本包快照自该定位的项目）。若未来迁移到真实生产项目，需按风险裁剪（如：度量改为 DORA 全量、引入 CI/PR、QA 门禁按团队节奏调优），**不能原样搬**——此声明在诊断记录基础上保留并强化。
