# 需求分级（L / M / S lane）——流程长度的横向裁剪

> 本文件为「新团队初始化包」快照副本（snapshot: 2026-09-13），泛化自来源仓库机制库（旧版本文档已清理，本文件为事实源）。

承接业界 L/M/S 需求分级实践与海天 run-mode（lite / stage-gated / through-run，见 `D:\OpenMausBot\.agents\product-workflow-suite\product-workflow\references\run-mode.md`）。**判定发生在指挥官澄清阶段**，与需求方对齐走哪条 lane，需求方也可直接指定。

| 级别 | 典型需求 | 流程 | 门禁 | QA run-mode | 产物与 skill 取用 |
|---|---|---|---|---|---|
| **L 大型 / 从 0** | 新功能、跨层改动（后端 + 前端 + 数据/迁移） | 完整流水线：澄清 → 规格 → 计划 → 对抗审查 → Reviewed → TDD → Review → Build → QA → Deploy | 全部门禁，一个不少 | through-run 或 stage-gated | 全产物集（clarify/prd/technical-solution/development-plan/test-cases）+ 全链 skill |
| **M 中型 / 单层** | 模块内功能增强、bug 修复 | 澄清 →（轻量计划）→ 对抗审查 → Reviewed → TDD → Review → QA | 保留人批 + QA；可简化或跳过正式 proposal | stage-gated（受影响层 + 关联场景） | 产物 = clarify + prd（可短写）+ development-plan + **test-cases**（QA 写，见原则 6）；technical-solution 可选（决策并入 prd/plan） |
| **S 小型 / 快速迭代** | 文案、样式、单点修复；文档改动 | 直接委派 Implement（或指挥官直接改）→ Build / QA 快速验证 | 跳过对抗审查与正式 proposal；写 git 代码仓库的改动仍要需求方过目确认 | lite（快速判定或 Not Applicable） | 最小集：implement/tdd + 快速验证；产物仅短 prd + 短 development-plan + 验证证据 |

## 关键原则

1. **分级是流程选择，不是门禁豁免**：L/M 保留状态机文件（Draft → Reviewed，Reviewed 只能人写）；S 级不强制建状态机文件，但任何写 git 代码仓库的改动（代码/文档落库）仍需需求方过目确认；QA 门禁判定（QA-Pending → QA-Passed / QA-Blocked）在各级都保留，S 级走快速判定。
2. **纯文档型改动**（README、笔记、说明）默认 S 级或 Not Applicable，由指挥官判断，不强制 Build/QA。
3. **S/lite 排除条件**（不满足任一条就不得降级）：已有产品/接口/规则上的增量小改（不是从 0 到 1）；只改一个按钮/字段/接口/规则；影响不超过一个模块、预计一天内完成；不涉及新权限模型、敏感数据、schema/迁移、跨仓契约、架构边界或高风险发布；项目级事实（代码位置、验证命令）可轻量探查确认。涉及新权限/敏感数据/迁移/跨仓/架构时**必须**走 L 或 M。
4. **fog（不确定高）时保持谨慎**：缺目标用户或触发场景、验收不可判定、存在 blocker 时不得降级到 S/lite；即使用户点名快速完成，也先问一个问题对齐。
5. **判定产出**：分级结果写入 `.workflow-state.json` 的 `run_mode`（lite / stage-gated / through-run），并作为澄清结论的一部分（L/M 写进 clarify.md）。
6. **测试产物判定（业界口径，各级不豁免）**：可自动化的验收标准写进测试代码（集成/单元测试），test-cases.md 中对自动化覆盖的 AC 只做**一行映射**（指向测试类/方法，不重复步骤）；**非自动化用例**（手动/浏览器走查/E2E/环境/性能/安全）必须完整写入 test-cases.md——「可自动化的写代码，不可自动化的写文档」，不允许有第三种丢失状态。technical-solution.md 是唯一允许按级别裁剪的产物（L 必产 / M 可选），test-cases.md 不裁剪。
7. **度量闭环（v2）**：每切片在 `.workflow-state.json` 顶层记 `metrics` 三个数——`lead_time_to_reviewed`（澄清→Reviewed 前置时间，Reviewed 写入时记）、`rework_count`（实现→QA 通过期间缺陷返工次数，QA 判定时记）、`qa_first_pass`（QA 是否一次通过，QA 判定时记）。撑起对账闭环（04-约束链与对账.md）的量化部分，与定性对账互补，不硬套 DORA 四指标。
8. **CI 等价门禁（v2 正名）**：构建与验证是 Reviewed 之后、QA 之前的**固定闸**（状态机已锁死该顺序）；单机环境无 push 即 CI 的客观条件，不引入伪 CI——此闸即 CI 等价物，构建行标注「CI 等价门禁，固定闸」。
9. **覆盖率风险分级（v2）**：核心业务模块（后端服务层等）测试覆盖率 ≥ 80%；工具 / 脚本 / 演示页不设阈值。TDD 保证「有测试」，阈值保证「测到关键处」，两者互补；QA 环节按此执行。
10. **分支/PR 有意选择（v2 决策记录）**：保持直接 commit 主分支 + 流程内双审查（对抗审查 + 代码审查），不引入短命分支/PR——单人 + 单机场景下分支是纯负担，双审查已覆盖 PR 核心价值。**触发变更条件：进入多人协作 / 多机协作时重开此决策**。
11. **S 级 TDD 裁定（v2，需求方原话）**：「S 级别的 tdd 就足够了，不用那么测试；如果需要比较严谨的测试，就不应该归类为 S 级。」——S 级 TDD 保持强制、不开口子；**分级本身承担风险裁剪**，需严谨测试的需求按定义归 M/L。
12. **度量复盘机制（v2.1 补充）**：原则 7 只定义了「记数」，本原则补「用数」——**聚合点**：`协作机制/11-度量台账.md`（每切片一行：需求 / lane / 三数 / 备注），指挥官在 Reviewed 写入时记 `lead_time_to_reviewed`，收到 QA 判定后补记另两数（QA 是只读 bot 不写状态机，记数责任归指挥官）；**复盘节奏**：切片级即时记数 + **每 3~5 个切片或每月一次复盘**（指挥官主持、与需求方对齐，文档型任务不广播）；**阈值信号**：M/L 级 `lead_time_to_reviewed` 超 3 天须写原因、`rework_count ≥ 2` 须写根因、`qa_first_pass = false` 必须写缺陷摘要；**复盘产出**：保留 / 调整 / 废弃某机制 → 写进《协作机制/10-优化方案决策.md》→ 决策表（02-场景决策表.md）据此刻意修订——与 04-约束链与对账.md 定性对账闭环合并成「定性对账 + 量化度量 + 定期复盘」三段闭环。**记录纪律**：QA 判定后 24h 内补记，不允许出现「走完流水线 metrics 为空」的切片（首例教训：首个切片补记时 `lead_time_to_reviewed` 因未记录澄清起点时间戳标「数据缺失」，无法回溯）。
13. **时间线记录（v2.3 补充）**：原则 12 的 `lead_time_to_reviewed` 只有总前置时间，补**环节级时间线**——`.workflow-state.json` 顶层新增 `timeline` 数组，每环节一项 `{stage, started_at, ended_at, duration, note}`；**记录责任归指挥官**（状态机唯一写入者）：委派发出时记 `started_at`，阶段状态写入（Reviewed / QA-Passed / Not Applicable）时记 `ended_at` 与 `duration`；**实时记、不事后补**，无法回溯的字段标 `null` 并在 note 说明，禁止虚构；`duration` 由相邻时间戳计算（含等待人批时间）。聚合：度量台账「环节耗时」列引用 `timeline`。首例教训：首个切片 clarify~对抗审查阶段未实时记起点，补记时仅可考若干离散节点，中间环节耗时标 null 不可回溯；QA 判定时间戳与构建收尾存在跨 bot 时钟/写入时序差异，已如实标注。

**对应关系速记**：需求侧 L/M/S ↔ 验证侧 run-mode（through-run / stage-gated / lite）↔ 产物集（全 / 精简 / 最小）↔ skill 集（全链 / 精简 / 最小）。
