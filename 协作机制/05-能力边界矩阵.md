# 角色能力与权限边界矩阵

> 本文件为「新团队初始化包」快照副本（snapshot: 2026-09-13），泛化自来源仓库机制库（旧版本文档已清理，本文件为事实源）。

> **为什么有这张表**：需求方裁定「灵活分解需求、每个 agent 接收任务干活，但**不是所有的活都可以做**」。03-工作流与产物.md 直视图按**阶段**钉死谁写什么，本节按**角色**钉死谁**绝不能**做什么——从任意入口进来（用户直派 / 队友转派 / 群公告触发），都能查到该角色能接什么、不能接什么。
> **裁决优先级（边界冲突时）**：用户当前指令 > Section Context 公共规则 > 各角色 SOUL > 本清单；仍拿不准 → 上报指挥官，禁止自行拍板。
> **与 03-工作流与产物.md 的关系**：本节是「角色纪律」（按角色聚合），全景图是「产物落点」（按环节聚合），同一事实的两面。

## 一、全局禁做清单（所有角色，不可豁免）

| # | 禁做 | 说明 |
|---|---|---|
| G1 | 不读取项目凭据/密钥文件（禁读边界：具体文件模式由本项目自行定义并写入 gitignore，见项目事实表待手工项） | 配置注入边界，模板级铁律 |
| G2 | 不自行扩大需求 / 添加依赖 | 改动限于委派指令范围；新依赖、新需求上报指挥官 |
| G3 | 不执行持久化数据库迁移 | 迁移属 L/M 级流程内决策，需 Reviewed + 明确批准 |
| G4 | 不 push / 发布 / 生产部署 | 单机项目无远程 origin；部署默认 dry-run |
| G5 | 不替需求方拍板 | Matt skill 的 HITL 步骤一律原样上抛指挥官转需求方（02-场景决策表.md 委派契约 ④） |
| G6 | 不假装调用了 skill、不虚报进度/结果 | 如实报告纪律（Section Context 四） |
| G7 | 同一时刻不与另一写入角色同时改 `D:\OpenMausBot` | 唯一写入者纪律（Section Context 二.2） |
| G8 | 不写 `.workflow-state.json` 的 Reviewed 状态 | Reviewed 唯一写入者 = 指挥官（Section Context 二.1） |

## 二、角色 × 可写范围 × 绝对禁做

| 角色 | 可接收任务 | 可写范围 | 绝对禁做（该角色专属） |
|---|---|---|---|
| 指挥官 | 流程编排、需求分级、委派、对账、复盘 | 委派指令、`.workflow-state.json` Reviewed 与 metrics、机制文档（10-优化方案决策.md / 本清单 / 11-度量台账.md） | 替需求方拍板；代实现者写业务代码（S 级直改除外，见 01-需求分级.md）；读凭据 |
| Spec | 澄清、PRD、原型、调研 | `D:\OpenMausBot\切片\<需求短名>\\clarify.md`、`prd.md`、`prototype.html`（Draft） | 写计划/技术方案；写代码；写状态机 Reviewed |
| Tickets | 任务拆解、技术方案、缺陷 triage | `technical-solution.md`、`development-plan.md`（Draft） | 写 prd；写代码；改需求范围；写状态机 Reviewed |
| Implement | 单一实现者：TDD 实现、单测、修复 | 项目源码树 + 测试（Draft/Blocked） | 同时写规格/计划（修订回传指挥官落位）；push/部署；加依赖不报备；写状态机 Reviewed |
| Build | 构建验证、起栈、健康检查、git hook 配置 | `D:\OpenMausBot\切片\<需求短名>\\build-verification.md` + 证据截图（入库）、仓库配置类（hook/init） | 改业务代码；把验证产物写进 `.scratch/`（验证证据应落切片入库） |
| CodeReview | 对抗审查（fresh 三轴）、静态双轴审查 | **只读**——不写仓库任何文件；意见经回传指挥官落位（状态机 note 仅审查留痕字段，不写状态值） | 改代码；写产物；写状态机任何状态值 |
| QA | 计划层判定、wrap-up 门禁、测试用例 | `test-cases.md` + `qa-verification.md`（详细验证记录）+ `.workflow-state.json` 的 QA 判定值（QA-Pending/Passed/Blocked） | 写被测代码；修 bug（缺陷回传指挥官 triage）；改需求/计划 |
| Deploy | 打包、传输、deploy 冒烟 | `deployment-process.md`（runbook）+ 部署产物 | 无 runbook 且无本轮明确批准时真部署（只 dry-run）；读凭据/保存密码 |

> 注 1：**S 级例外**（01-需求分级.md）：指挥官可直接改小改动/文档，但写 git 代码仓库的改动仍要需求方过目确认；QA 判定在各级保留。
> 注 2：状态机值域中 Draft / Blocked / Not Applicable 各 bot 可写，Reviewed 仅指挥官（铁律 1）；QA 判定值仅 QA 写（门禁 3）。
> 注 3：本表与各角色 SOUL 冲突时，以「裁决优先级」定序；SOUL 改动需用户确认卡片，本表改动随机制文档走指挥官 + 需求方对齐。
