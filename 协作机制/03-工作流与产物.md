> 本文件为「新团队初始化包」快照副本（snapshot: 2026-09-13），泛化自来源仓库机制库（旧版本文档已清理，本文件为事实源）。

## 一、落地步骤（新项目复用模板的完整流程）

1. **生成模板**：按当前 8 角色 SOUL 提炼成 `<slug>-team.botmrr.md`（通用核心 + 占位符，机器路径与项目规范外置；本项目由初始化脚本按 slug 生成）；
2. **导入**：桌面端 Teams → Import（project 模式可绑定新目录 + 自动开房间）；重名角色显示为 "New copy of X"，不覆盖现有角色；
3. **设 cwd**：把每个新 bot 的 working folder 指到项目目录；
4. **对技能**：按 02-场景决策表.md 映射表确认 `D:\OpenMausBot\.agents` 技能库就位（模板不内联 skills，包上限 20 且丢非 md 文件）；
5. **填占位符**：按 09-项目事实表.md 逐项替换 SOUL 中的占位符（初始化脚本已替换必替项；保留待手工项按占位登记表填写）；
6. **验证**：跑一个真实需求走完整流水线，闭环后再固化回模板。

## 二、工作流对照（SDD 阶段 ↔ 海天产物 ↔ 状态机）

两套流程状态机同构（Draft / Reviewed / Blocked / Not Applicable），统一口径：**产物命名用海天，门禁用 SDD**。

| SDD 阶段 | 海天阶段/产物 | 状态机取值 | 门禁 |
|---|---|---|---|
| 需求澄清 | `clarify.md` | Draft | 澄清完整才能进规格 |
| 规格 | `prd.md`、可选 `prototype.html` | Draft | 三轴对抗审查通过 |
| **Reviewed（人批）** | — | **Reviewed（只能指挥官写）** | **人批准，最贵的一道闸** |
| 任务计划 | `technical-solution.md`、`development-plan.md` | Draft | 计划含验证命令与写入范围 |
| TDD 实现 | 代码 + 单测 | Draft/Blocked | 测试真绿才报完成 |
| 代码审查 | （代码 diff） | Draft | 静态双轴审查 |
| 构建与验证（CI 等价门禁，固定闸） | `build-verification.md` + 健康检查 | Draft | 真实 PASS 输出 |

### 接缝与规则（Matt 默认 vs 本项目约定）

1. **Matt 默认位置不同**：`to-tickets` 原文默认写 `.scratch/<slug>/issues/<NN>-<slug>.md`；本项目映射为 `D:\OpenMausBot\切片\<需求短名>\\development-plan.md`（第二节工作流对照）。**委派指令必须指名海天路径**，否则子 bot 可能按 Matt 默认落盘。
2. **验证证据入库 + .scratch 纯过程区**：验证证据（build-verification.md / qa-verification.md / 证据截图）**默认直接落 `D:\OpenMausBot\切片\<需求短名>\\` 入库**，不再先写 `.scratch/` 再手动转正；`.scratch/` 仅为纯过程区（日志、临时脚本、演练草稿），gitignore，**整目录可随时删除，删除零信息损失**。**验证必须附截图（审计门禁）**：凡涉及 UI 的验证环节（Build 起栈冒烟 / QA 浏览器走查），验证通过必须附截图入库，供人工审计复盘——Build 留 `build-smoke.png`；QA 走查**逐项**留 `qa-<NN>-<slug>.png`（NN=走查表序号）；截图必须在 build-verification.md / qa-verification.md 中逐项引用——引用形式固定为 markdown 图片语法 `![描述](文件名)`（纯文字/backtick 提及不算引用，审计按图片语法反查，未引用的截图视为未交付）；纯 API/命令行验证（无 UI 断言）免截图但须注明"无 UI"。
3. **wayfinder 级**：触发判据 = **超大 + 雾状**——大到装不进一个 agent 会话，且从当下到目的地"看不见路"；方向已清楚只是体量大 → 直接 L 级全链流水线，**不触发**（探路产出的是决策不是交付物，map 完成即 handoff）。
   - **产物形态**（本地 markdown，无 issue tracker）：
     ```
     D:\OpenMausBot\切片\<需求短名>\\wayfinder\
     ├── map.md                  # Destination / Notes / Decisions-so-far / Not yet specified / Out of scope
     └── tickets/
         ├── 01-<决策名>.md      # ## Question + claim: <角色> + Type: research|prototype|grilling|task + Status: <待办|已认领|已解决>（取值以 wayfinder skill 为准）
         └── 02-<决策名>.md
     ```
   - **执行纪律**：一次委派 = 一个 ticket（委派指令指名 `wayfinder` skill）；ticket 头部 `claim` 字段**先认领再动工**（防并发抢写）；map 的 Decisions-so-far 由**指挥官统一追加**（沿用单一写入者铁律，禁止两个写入角色同时改 map）；决策只存一处——ticket 内写全，map 只留一行 gist + 链接，不重述。
   - **HITL**：grilling / prototype 型 ticket 遇需求方才能拍板的问题，子 bot **原样上抛指挥官 → 转需求方 → 回传，禁止自答**（沿用 02-场景决策表.md 委派契约 ④）。
   - **状态机**：map 用 `Draft → Reviewed`（Reviewed 只指挥官写，批准即方向认可）；tickets 用「待办 / 已认领 / 已解决」三态（取值以 wayfinder skill 为准）；与切片状态机并存，互不冲突。
   - **合流**：map 完成 = destination 明确 → 指挥官定 L/M/S → 拆进现有 11 步流水线（wayfinder 是流水线**前置探路阶段**，不替代、不绕过 L/M/S）。
4. **diagnosing-bugs（接缝）**：根因分析暂无独立落点；约定先写进 `development-plan.md` 对应任务（或 `D:\OpenMausBot\切片\<需求短名>\\` investigation note，草稿可在 `.scratch/`），真遇到 bug 需求时再细化。
5. **审查意见无独立文件**：对抗 / 代码审查意见靠状态机 note + 计划修订留痕（已实践），不另开产物文件。
6. **测试范围分级（需求方裁定）**：验证执行**默认只覆盖本需求相关范围**，不默认全量跑整个项目。验证对象 = 本切片新增/修改的测试类 + 因改动触达而受影响的关联面；**全量回归仅在** (a) 改动触及核心共享层（token/拦截器校验、全局异常处理、公共基类/工具类、DB schema、公共请求封装）导致影响面无法收敛，或 (b) 需求方/指挥官明确要求时执行。判定责任链：Tickets 在 development-plan 每个任务写明「验证命令 + 测试范围与关联面依据」→ Implement 按此执行 → QA 计划层判定核对（IDENTIFY 先列本轮范围，再 RUN，复跑同样按范围收敛，不无脑全量）。test-cases.md §2 项目测试上下文**必写「本次测试范围 + 关联面依据」**，不再默认整段全量回归命令。**构建门禁不受此约束**（`npm run build` / `mvn` 编译仍全量执行，静态门禁成本低），本分级只约束**测试执行**范围。先例：改动触及核心共享层（拦截器校验触达全部接口）时全量合理；改动收敛于单模块时按关联面收敛、零回归。

7. **验证证据审计判定标准（审计门禁基线先例）**：验证证据是否合格按以下矩阵审计（指挥官执行，纯只读，不写入仓库）：
   - **截图门禁**（规则 2）：Build 有 `build-smoke.png` 且 build-verification.md 有 markdown 图片引用；QA 走查**逐项**有 `qa-<NN>-<slug>.png` 且 qa-verification.md 逐项引用；**未引用=未交付**；纯 API/命令行验证须注明"无 UI"。
   - **测试范围**（规则 6）：test-cases.md §2 写明「本次测试范围 + 关联面依据」；QA 实际执行命令不超出声明范围；全量回归必须命中两个触发条件之一（核心共享层改动 / 需求方或指挥官明确要求）。
   - **对账方法**：`git log --name-only` 还原切片实际改动 → 判定触达面（是否碰拦截器/token 校验/全局异常/公共基类/schema）；png 清单 vs markdown 图片引用反查；「声明范围 vs 实际命令 vs 触达面」三对照。
   - **两档判定**：门禁生效后的切片按新标准硬判；门禁前切片按当时标准判定 + 诚实标注历史缺口（不伪造合格）。
   - **审计边界**：只验留档（截图存在且被引用、命令不超范围），**不重新证明截图内容真实反映当时页面**——报告区分「留档合格」与「内容待人工复核」；留档缺失时靠 git diff 反推并标注「推断」而非「核实」。
   - **节奏**：每 3~5 切片或月度与度量复盘同频批量审计（便于横向对比与趋势），单切片轻量约 1 分钟；每次产出逐切片判定表 + 依据 + 耗时统计。
   - **报告归档**：审计报告入库 `D:\OpenMausBot\审计\<日期>-<主题>-审计.md`（git 版本化，可追溯），不留存在任务工作区。
   - **行动建议必配（审计闭环）**：每次审计除判定表外必产行动建议清单——每条含「问题 / 建议动作 / 影响面 / 风险分级（低中高）/ 建议审批人」。审计的目的是修订完善，不是留档了事。
   - **审批分级**：低风险记录补全类（补 timeline、补引用、无规则变更的文档修正）由指挥官自批执行并在报告登记；机制规则修订（改协作机制/模板）、历史产物补写或改写、范围扩大、方向性建议 → 上抛需求方审批，上抛必须附「建议内容 + 涉及产物路径 + 核实方式」（需求方可能手动核实产物后再批，空手问不算审批请求）。上抛形式遵守 02-场景决策表.md 委派契约 ⑤：审批/决策请求优先用问题卡片（ask_user_question）二选一直接问、回答回传会话；**非必要不发 OMB native-approval 审批弹窗**（点击决策不回传会话的已知缺陷）；需需求方补充信息时先问「是否愿意填写」，同意后由需求方在聊天输入框自行补充。
   - **修订复核闭环**：审批通过 → 执行修订 → 报告「行动建议跟踪表」登记（审批人/状态/commit）→ 下一轮审计复核未闭环项，未闭环须说明原因。

**长期迭代判断（现状合理，三个建议现阶段无需动作）**：

- **合理处**：四层分离清晰——`切片/`（正式产物**含验证证据**，全部入库，可审计）+ `.scratch/`（纯过程区，gitignore，整目录可随时删除）+ `协作机制/`（机制，入库）+ `.agents/`（技能库，版本化）；状态机就近放每切片目录（单一事实源）。
- **建议 1**：切片数增长后（约 >10）在 `切片/` 加 `index.md`（需求清单 + 状态速览），避免靠目录扫读失效率。
- **建议 2**：完成的切片以状态机 terminal 状态为归档标记，未来可整目录归档 / 压缩，现阶段无需动作。
- **建议 3**：状态机 note 是审查留痕的唯一落点，写入者要写全（已实践良好，保持）。
