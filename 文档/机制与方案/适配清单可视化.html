5需求分级 L / M / S（流程长度的横向裁剪）

判定发生在指挥官澄清阶段，与需求方对齐；分级写入 .workflow-state.json 的 run_mode。分级是流程选择，不是门禁豁免。

L大型 / 从 0

新功能、跨层改动（后端+前端+数据/迁移）
  • 完整流水线，全部门禁一个不少
  • run-mode：through-run / stage-gated
  • 全产物集 + 全链 skill

M中型 / 单层

模块内功能增强、bug 修复
  • 澄清 →（轻量计划）→ 对抗审查 → Reviewed → TDD → Review → QA
  • 保留人批 + QA；可简化或跳过正式 proposal
  • technical-solution 可选；test-cases 不裁剪

S小型 / 快速迭代

文案、样式、单点修复；文档改动
  • 直接委派 Implement → Build / QA 快速验证
  • 跳过对抗审查与正式 proposal
  • 写 git 代码仓库的改动仍要需求方过目
  • TDD 保持强制、不开口子
⛔ S/lite 排除条件（不满足任一条就不得降级）：增量小改（非从 0 到 1）；只改一个按钮/字段/接口/规则；影响不超过一个模块、预计一天内完成；不涉及新权限模型、敏感数据、schema/迁移、跨仓契约、架构边界或高风险发布。fog（不确定高）时不得降级；即使用户点名快速完成，也先问一个问题对齐。
📌 关键原则 7–11（v2 落地）：⑦ 度量闭环——metrics 三数（lead_time_to_reviewed / rework_count / qa_first_pass）记入 .workflow-state.json 顶层；⑧ CI 等价门禁——构建验证 = Reviewed 后、QA 前固定闸；⑨ 覆盖率风险分级——核心业务 ≥80%，工具/脚本/演示页不设阈值；⑩ 分支/PR 有意选择——直接 commit 主分支 + 流程内双审查，多人协作时重开决策；⑪ S 级 TDD 裁定——"需要严谨测试就不该归 S 级"，分级承担风险裁剪。

6合理性保障：四层约束链 + 对账闭环

机制前提（如实说明）：场景判断与 skill 选择是模型概率判断，给不了硬保证；合理性靠四层约束链让不合理判断"无处藏身"，靠每轮对账闭环持续收紧。

↻ 对账闭环：每完成一个需求——实际走的链条 vs §3.1 决策表预测 → 偏差（误判/断链/表不适用）记入复盘 → 修正决策表或 SOUL。三条诚实边界：① 看不到被委派 bot 是否真调用了 skill，契约层留痕是间接验证的闭环关键；② 调了 skill ≠ 做得好（skill 是提示词非程序），质量终审押在对抗审查 + QA；③ 场景判断是概率，规则层写得越具体，"我认为"占比越低。

7角色能力与权限边界矩阵（适配清单 §8，v2.2 新增）

回答"哪些活能干、哪些绝对不能干"：全局禁做 + 角色×可写范围×绝对禁做 + 裁决优先级。集中可审计，替代散落各 SOUL 的口头约定。

全局禁做 G1–G8（所有角色）

  • G1 不读取/输出项目凭据密钥文件（/.local-credentials.env 禁读）
  • G2 不自行扩大需求、不加未经批准依赖、不执行持久化迁移
  • G3 不 push / 发布 / 生产部署；测试部署默认 dry-run
  • G4 不替需求方拍板（HITL 上抛契约：问题原样上报指挥官转问）
  • G5 不虚报进度/结果，不把"生成命令/之前跑过"当证据
  • G6 不假装调用了 skill、不虚报进度/结果（如实报告纪律）
  • G7 同一时刻不与另一写入角色同时改 E:\Demo（唯一写入者纪律）
  • G8 不写 .workflow-state.json 的 Reviewed 状态（Reviewed 唯一写入者=指挥官）
角色可写范围绝对禁做
指挥官状态机 Reviewed；机制文档（协作机制/）替需求方拍板；push/发布/生产部署；读凭据
Spec切片 clarify.md / prd.md业务源码/测试/构建/凭据；替需求方定需求
Tickets切片 development-plan.md / technical-solution.md；缺陷跟踪业务代码；改规格（发现问题上报）
Implement业务源码 + 单测（单一实现者）计划/规格；未经批准依赖；无关文件；写 Reviewed
CodeReview只读改文件/提交/部署；读凭据；无证据声称通过；写仓库（含用户直接指示）
Buildbuild-verification.md + 截图落切片（入库）业务源码；自动杀进程；连远程测试服；把构建成功当测试成功
QA只读被测代码；test-cases.md / qa-verification.md、走查截图（逐项）与 QA 判定改被测代码/提交/部署；放宽阈值换通过；与写入角色并发跑 E2E；写仓库（含用户直接指示）
Deploy测试环境（默认 dry-run）生产部署；索要/保存/输出密码；sshpass；未经批准的传输与执行；失败自回滚
⚖️ 裁决优先级（边界冲突时）：用户当前指令 > Section Context 公共规则 > 各角色 SOUL > 适配清单；仍拿不准 → 上报指挥官，禁止自行拍板。多入口趋同：公共规则（OMB Section Context 全组注入）+ 各角色 SOUL 入口归一条款双保险——单独使用任一角色时行为与全组一致。
