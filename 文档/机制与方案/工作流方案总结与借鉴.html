1背景与裁定

方案源自 2026-09-12 机制对齐讨论，经 澄清 → 规格 → 计划 → 对抗审查 → Reviewed → 落地 成形。
需求方裁定Demo 的需求与功能是演示级，但工作流、skills、交付物、agent 协作均为生产级要求 → 设计目标是"生产级机制的完整性"，不是"放松流程"；流程重量本身是交付物的一部分。

3需求分级 L / M / S：流程长度的横向裁剪

判定发生在指挥官澄清阶段，与需求方对齐；分级写入 .workflow-state.json 的 run_mode（lite / stage-gated / through-run，取海天口径）。分级是流程选择，不是门禁豁免——Reviewed 人批与 QA 判定各级保留。

L大型 / 从 0

新功能、跨层改动（后端+前端+数据/迁移）
  • 完整流水线 11 步，全部门禁
  • run-mode：through-run / stage-gated
  • 全产物集 + 全链 skill

M中型 / 单层

模块内增强、bug 修复
  • 澄清 →（轻量计划）→ 对抗审查 → Reviewed → TDD → Review → QA
  • 保留人批 + QA；technical-solution 可选
  • run-mode：stage-gated

S小型 / 快速迭代

文案、样式、单点修复、文档改动
  • 直接委派 Implement → 快速验证
  • 跳过对抗审查与正式 proposal
  • 写 git 代码仓库的改动仍要需求方过目
  • TDD 保持强制、不开口子
  • run-mode：lite
⚑ S/lite 排除条件：涉及新权限模型 / 敏感数据 / schema/迁移 / 跨仓契约 / 架构边界 / 高风险发布时必须升 L 或 M；fog（不确定高）时保持谨慎，不得降级。速记：需求侧 L/M/S ↔ run-mode（through-run / stage-gated / lite）↔ 产物集（全 / 精简 / 最小）↔ skill 集（全链 / 精简 / 最小）。测试范围（2026-09-13 补）：验证执行默认只覆盖本需求相关 + 受影响关联面（development-plan 写明依据），不默认全量；全量回归仅当改动触及核心共享层（拦截器/全局异常/公共基类/DB schema）或需求方/指挥官明确要求；构建门禁仍全量，分级只约束测试执行。验证审计（2026-09-13 补）：按协作机制 03 接缝规则 7 审计（指挥官纯只读）——截图门禁（引用形式固定 markdown 图片语法，未引用=未交付）+ 测试范围三对照（声明 vs 实际命令 vs git diff 触达面）；门禁生效后硬判、门禁前按当时标准+诚实标注；每 3~5 切片或月度批量审计。审计闭环（同日补）：报告归档 审计/ 入库；每次审计必配行动建议清单并分级审批——低风险记录补全指挥官自批，机制修订/历史产物改写/范围扩大上抛需求方（附产物路径与核实方式）；审批后修订并登记跟踪表，下轮审计复核。

4流水线与状态机：L / M / S 三条 lane 对照

状态机规则：AI 只能写 Draft / Blocked / Not Applicable；Reviewed 只能指挥官写（人批准，最贵一道闸）；QA 环节 QA-Pending → QA-Passed / QA-Blocked；状态机不可跳步（显式锁步）。三档流程列依适配清单 §4.5；符号：✓ 保留 · ⛔ 门禁 · ★ 人批 · ✓ CI 等价门禁 · 简化 裁剪 · ✕ 跳过/未列。
★ Reviewed = 人批准（最贵） ⛔ QA = Gate Function 门禁 构建验证 = CI 等价门禁，固定闸 状态机不可跳步

差异速读 —— 主要是少了什么（依据 §4.5 官方流程列）
M 比 L 少：独立规格步（prd 短写）、正式技术方案（technical-solution 可选，决策并入 prd/plan）、构建验证独立闸（流程列未显式列；实战 QA 前仍做）、部署步。保留：对抗审查 ⛔、Reviewed ★、TDD、代码审查、QA ⛔（stage-gated）。
S 比 M 再少：对抗审查（跳过）、Reviewed 正式人批（写 git 代码仓库的改动仍需求方过目确认）、代码审查、正式计划（仅短 prd + 短 development-plan）。保留：TDD 强制（不开口子）、QA 快速判定（lite）、构建快速验证。
各级不豁免：TDD 强制 + QA 判定 + Reviewed（L/M 走状态机人批，S 走需求方过目）——分级是流程选择，不是门禁豁免；纯文档型改动默认 S 或 Not Applicable。

9与 Matt 单 agent skill 方式对比

Matt 方式：单 agent 全栈，一条主线流程 + 技能路由器 ask-matt（人触发）+ 上下文卫生 + on-ramps + 词汇层；agent 直接对用户。

相同点（我们借鉴了什么）

Matt 概念Demo 对应借鉴方式

to-spec / to-tickets 垂直切片Demo-Spec / Demo-Tickets 产出 prd.md / development-plan.md原 skill 指名调用
tdd / implement（RED-GREEN）Demo-Implement 单任务 TDD原 skill 指名调用

wayfinder（超大任务探路）决策表"超大任务/方向不明"行 + 适配清单 §4.7 接缝规则 3（2026-09-12 补全）思想采纳，落地形态已定义

不同点

维度MattDemo不同为了什么
执行主体单 agent 全栈，上下文连续1 指挥官 + 7 专家，委派协作职能隔离 + 独立校验：写方案≠写代码≠审查≠验证；对抗审查 fresh 上下文彻底隔离调用方判断
与需求方关系agent 直接对用户指挥官代理需求方；HITL 问题上抛需求方单一接触点；子 bot 无需求方通道，决策权集中到人闸
并发控制单 agent 无并发问题单写入者纪律 + 状态机多 bot 同仓防冲突，写入可审计
上下文管理窗口卫生（compact/handoff）外部持久化状态机 + fresh 上下文审查多 bot 无法共享内存，状态必须外置、就近、单一事实源
流程重量轻（鼓励直接 implement）显式锁步（不可跳步、S 级 QA 不豁免）流程演练项目，流程重量是交付物
度量无显式量化闭环每切片 3 个数复盘可量化，成本≈0
本质分野：Matt 的连续性在上下文窗口里，Demo 的连续性在仓库的产物与状态里——拆开的主体靠文档与状态机重新粘合。

11学习借鉴总结（重点）

Matt我们学到什么

  • 方法论，不重造：TDD 节奏、垂直切片、先红后修、对抗访谈、深模块词汇——30 个技能直接成为执行层主力
  • 技能路由器思想：ask-matt 让人导航技能；Demo 把导航职责内化为指挥官 + 决策表，路由由人点变成查表可得
  • HITL 的价值：访谈/quiz/质询坚持"决策是用户的"，Demo 继承为 HITL 上抛契约——子 bot 不许替需求方拍板

海天我们学到什么

  • 骨架与命名：11 阶段流水线、海天命名产物、状态机、run-mode 三级、lite 排除条件——流程骨架直接以海天为底
  • 门禁语义：每阶段"过了才进下一步"、对抗审查三轴（自评不算过）、wrap-up 收尾——最值钱的部分，全盘继承并加严
  • 裁剪哲学：lite 判定条件逐条继承为 S 级排除条件——轻重是有据的裁剪，不是随意的偷懒
💡 为什么有不同点：全部服务于同一个目标——"生产级机制完整性"裁定下，让多 bot 协作达到单 agent 时代无法达到的隔离度与可审计性。一句话：Matt 给了我们"怎么把一件事做对"的方法，海天给了我们"一套完整流程长什么样"的骨架；我们把方法装进骨架，再按多 bot 协作与生产级可审计的目的改造执行层。
