3怎么保证判断与协作"合理"？——四层约束链

判断本身是概率，给不了硬保证；但可以让不合理判断无处藏身。质量终审不依赖"调用方自证"，依赖独立校验。

① 规则层 · 查表

把临场判断变成查表
  • 决策表固化进协作机制/02-场景决策表.md
  • 我的每次选择可对账：偏差当场可见
负责人：指挥官 + 文档

② 契约层 · 留痕

委派指名 + 产物标注
  • 委派写死："用 to-spec 产出 prd.md"
  • 产物 header 标注 skill 痕迹
  • 每环有可审计指纹，事后可翻验
负责人：指挥官委派指令

③ 校验层 · 独立

对抗审查不信我
  • Demo-CodeReview fresh 上下文，不带我的判断结论
  • 三轴审查：必要性 / 可行性 / 风险
  • 判断错了或 skill 用错，方案硬伤在 Reviewed 前被揪出
负责人：Demo-CodeReview（只读）

④ 门禁层 · 人闸

最贵的闸是人
  • Reviewed = 人批（只有指挥官能写）
  • QA 门禁 QA-Pending → Passed / Blocked
  • 状态机锁死顺序，不可跳步
负责人：需求方 + 状态机

6多入口归一与公共规则（2026-09-12 生效）

OMB 多 bot 无共享记忆，多入口趋同做不到 Grok Build 的构造性趋同（单脑），只能工程化围堵：公共规则 + SOUL 双保险 + 四层设计——单独使用任一角色时，入口行为与全组一致。
🧭 入口路由（每个角色自带）：收到业务需求（改代码 / 修 bug / 新增功能）→ 上报指挥官分级分派，不自行开工、不自行委托；收到只读咨询（问机制 / 问现状 / 问文档）→ 直接回答；收到明确委派 → 按委派契约执行。QA / CodeReview（只读角色）追加：收到写仓库请求（含用户直接指示）→ 说明只读边界并上报，不自行写入。
📜 公共规则（OMB Section Context）：桌面应用「团队地图」→ 分区卡片 → Context 按钮粘贴（只有用户能写，agent 禁写；上限 24000 字节）；内容每轮注入全组 prompt。Demo v1 已生效 = 入口归一 + 四条铁律（Reviewed 唯一写入者 / 唯一写入者纪律 / 门禁不可豁免 / 不越权）+ 事实源指针 + 协作姿态；留档 协作机制/demo-team-section-context.md。
⚖️ 能力边界矩阵（协作机制/05-能力边界矩阵.md）：全局禁做 G1–G8 + 8 角色 × 可写范围 × 绝对禁做 + 裁决优先级（用户当前指令 > Section Context > SOUL > 适配清单）。诚实边界：规则/状态/门禁三层围堵只能降低漂移、让偏差可审计，不能保证绝对趋同（模型概率本质）。

状态机（.workflow-state.json）

  • AI 只能写：Draft / Blocked / Not Applicable
  • Reviewed 只能指挥官写（人批准后才进实现）
  • QA 取值：QA-Pending → QA-Passed / QA-Blocked
Draft · Blocked · Not Applicable Reviewed（人） QA-Pending → QA-Passed / QA-Blocked

委派纪律（指挥官）

  • 先委派规格和计划，再委派单一实现者；实现后只委派只读 Review / 构建 / 验证
  • 同一时刻不允许两个写入角色同时改 E:\Demo；每次委派说明输入 / 输出文件 / 写入范围 / 验证命令
  • 没有部署 runbook + 本轮明确批准时，部署只能 dry-run
  • 看板只广播业务需求阶段状态；对话型 / 文档型 / 咨询型不广播
