## 一、背景与裁定

本方案从 2026-09-12 的机制对齐讨论逐步成形（澄清 → 规格 → 计划 → 对抗审查 → Reviewed → 落地），过程与结论记录在《工作流最佳实践诊断》与《工作流优化方案》。

**需求方裁定（2026-09-12 明确）**：Demo 项目的**需求与功能是演示级**，但**工作流、skills、交付物、agent 协作等机制均为生产级要求**。因此本方案的设计目标是"生产级机制的完整性"，不是"放松流程"；流程重量本身是交付物的一部分。

**技术栈**：Java 21 + Spring Boot（backend）/ Vue 3 + Vite + TS（frontend），本地 git（无远程 origin），本地 H2/MySQL，测试服部署默认 dry-run。

## 二、Demo 整体方案全景

### 2.1 团队组织：1 指挥官 + 7 专家

| 角色 | 职责 | 读写边界 |
|---|---|---|
| **指挥官（本 bot）** | 全流程协调、需求分级、委派、**Reviewed 唯一写入者**、批准与交付门禁 | 写状态机 Reviewed；其余只读协调 |
| Demo-Spec | 澄清→规格：`clarify.md` / `prd.md`（可选原型），验收标准 | 只写规格产物，不碰业务源码/测试/凭据 |
| Demo-Tickets | 任务拆解：`technical-solution.md` / `development-plan.md`；缺陷 triage | 只写计划与缺陷文件 |
| Demo-Implement | 单任务 TDD（RED-GREEN-REFACTOR），如实报告 | **单一实现者**，写代码 + 单测 |
| Demo-CodeReview | **fresh 上下文**三轴对抗审查（人批前）+ 静态双轴审查（实现后） | **只读** |
| Demo-Build | 起栈、构建、健康检查（CI 等价门禁） | 写 `build-verification.md` + 截图到切片（入库） |
| Demo-QA | 计划层判定 + wrap-up 门禁（Gate Function） | **只读**被测代码，写 `test-cases.md`、QA 判定与走查截图（逐项，审计门禁） |
| Demo-Deploy | 打包、传输、deploy 与冒烟 | **默认 dry-run**，双重批准 |

**写入纪律**：先委派规格 + 计划，再委派**单一实现者**；实现后只委派只读 Review / Build / QA。**同一时刻不允许两个写入角色同时改 E:\Demo**。

### 2.2 需求分级 L / M / S：流程长度的横向裁剪

判定发生在指挥官澄清阶段，与需求方对齐；分级写入 `.workflow-state.json` 的 `run_mode`（lite / stage-gated / through-run，取海天口径）。

| 级别 | 典型需求 | 流程 | 门禁 | run-mode |
|---|---|---|---|---|
| **L 大型 / 从 0** | 新功能、跨层改动（后端+前端+数据/迁移） | 完整流水线 11 步 | 全部门禁 | through-run / stage-gated |
| **M 中型 / 单层** | 模块内增强、bug 修复 | 澄清 →（轻量计划）→ 对抗审查 → Reviewed → TDD → Review → QA | 保留人批 + QA | stage-gated |
| **S 小型 / 快速迭代** | 文案、样式、单点修复、文档改动 | 直接委派 Implement → 快速验证 | 跳过对抗审查与正式 proposal；**写 git 代码仓库的改动仍要需求方过目** | lite |

**关键原则**：
1. **分级是流程选择，不是门禁豁免**——Reviewed 人批与 QA 判定各级保留（S 级走快速判定）；
2. 纯文档型改动默认 S 或 Not Applicable，不强制 Build/QA；
3. **S/lite 排除条件**：涉及新权限模型、敏感数据、schema/迁移、跨仓契约、架构边界或高风险发布时**必须**升 L 或 M；
4. fog（不确定高）时保持谨慎，不得降级；
5. **S 级 TDD 保持强制、不开口子**（需求方裁定："S 级别的 tdd 就足够了，不用那么测试；如果需要比较严谨的测试，就不应该归类为 S 级"）——**分级本身承担风险裁剪**，需严谨测试的需求按定义归 M/L。

**对应关系速记**：需求侧 L/M/S ↔ 验证侧 run-mode（through-run / stage-gated / lite）↔ 产物集（全 / 精简 / 最小）↔ skill 集（全链 / 精简 / 最小）。
**测试范围（2026-09-13 补）**：验证执行**默认只覆盖本需求相关 + 受影响关联面**（development-plan 写明依据），不默认全量跑整个项目；全量回归仅当改动触及核心共享层（拦截器/全局异常/公共基类/DB schema）或需求方/指挥官明确要求。构建门禁（build）仍全量，分级只约束测试执行。

**验证审计（2026-09-13 补）**：验证证据按协作机制 03 接缝规则 7 审计（指挥官纯只读执行）——截图门禁（Build `build-smoke.png`、QA 逐项 `qa-<NN>-<slug>.png`，引用形式固定 markdown 图片语法 `![描述](文件名)`，未引用=未交付）+ 测试范围三对照（test-cases.md §2 声明范围 vs QA 实际执行命令 vs git diff 触达面，全量需命中触发条件）；门禁生效后切片硬判、门禁前按当时标准+诚实标注历史缺口；节奏=每 3~5 切片或月度与度量复盘同频批量审计（单切片约 1 分钟），报告区分「留档合格」与「内容待人工复核」。**审计闭环（同日补）**：报告归档 `E:\Demo\审计\` 入库；每次审计必配行动建议清单并分级审批——低风险记录补全（补 timeline/引用）指挥官自批，机制修订、历史产物补写/改写、范围扩大上抛需求方（附产物路径与核实方式）；审批后修订并登记「行动建议跟踪表」，下轮审计复核未闭环项。

### 2.3 完整流水线与状态机

```
业务需求 → 澄清 → 规格 → 任务计划 → 对抗审查（fresh） → Reviewed（人批）
        → TDD 实现 → 代码审查 → 构建验证（CI 等价门禁）→ QA 验证 → 测试环境部署
```

**状态机规则**（`.workflow-state.json`，就近放每切片目录 = 单一事实源）：
- AI 只能写 `Draft` / `Blocked` / `Not Applicable`；
- **`Reviewed` 只能指挥官写**（对应人批准，最贵的一道闸）；
- QA 环节取值 `QA-Pending → QA-Passed / QA-Blocked`；
- 状态机**不可跳步**（显式锁步）。

### 2.4 产物与路径安排：四层分离

| 层 | 内容 | 入库 |
|---|---|---|
| `切片/<需求短名>/` | 正式产物：clarify.md / prd.md / technical-solution.md（L 必产、M 可选）/ development-plan.md / test-cases.md / deployment-process.md + `.workflow-state.json` | ✅ git 落库 |
| `.scratch/<需求短名>/` | 纯过程区（日志、临时脚本、演练草稿）；验证证据已提升至切片入库 | ❌ gitignore，整目录可随时删除 |
| `文档/` | 给人看的机制方案与学习资料（机制与方案 / 团队模板 / 工程指南 / OMB学习笔记）；机制事实源在 `协作机制/` | ✅ git 落库 |
| `.agents/` | 技能库版本化（Matt 30 个 + 海天 19 个） | ✅ git 落库 |

**路径存储合理性判断（2026-09-12 结论，09-13 更新）**：现状**合理，适合长期迭代**——四层职责清晰；验证证据直接落切片入库（build/qa verification），`.scratch` 为纯过程区可整体删除（转正先例：deploy-dry-run → deployment-process）。长期建议（现阶段无需动作）：切片 >10 个加 `index.md`；完成切片以状态机 terminal 态作归档标记；状态机 note 写全（审查留痕唯一落点）。

### 2.5 委派契约与 HITL 上抛（可审计）

1. 委派指令**写死 skill 名**（"用 `to-spec` 产出 prd.md"），不写笼统描述；
2. 切片产物 header 标注来源 skill（调用痕迹）；
3. 显式指名即绕过 `disable-model-invocation`，无需修改第三方技能库；
4. **HITL 上抛契约**：子 bot 调 Matt skill 遇 HITL 步骤（check seams / quiz / 对抗质询），问题**原样上抛指挥官 → 指挥官转问需求方 → 答复回传；禁止子 bot 自答**。背景：Matt skill 是「agent 直接对用户」骨架，我们是「指挥官代理需求方」骨架，子 bot 没有对需求方的直接通道。

### 2.6 合理性保障：四层约束链 + 对账闭环 + 度量

| 层 | 机制 | 负责人 |
|---|---|---|
| ① 规则层 | 查表：§3.1 决策表固化"场景 → skill → 角色"，偏差当场可见 | 指挥官 + 文档 |
| ② 契约层 | 留痕：委派指名 skill + 产物标注，每环有审计指纹 | 指挥官委派指令 |
| ③ 校验层 | 独立：Demo-CodeReview **fresh 上下文**三轴审查，不带调用方判断 | Demo-CodeReview（只读） |
| ④ 门禁层 | 人闸：Reviewed 人批 + QA 门禁 + 状态机不可跳步 | 需求方 + 状态机 |

**对账闭环**：每完成一个需求加一步流程对账（实际链条 vs 决策表预测），偏差记入复盘，下一轮修正决策表或 SOUL。

**度量闭环（v2 补，轻量版）**：每切片在 `.workflow-state.json` 顶层记 3 个数——`lead_time_to_reviewed`（澄清→Reviewed 前置时间）、`rework_count`（实现→QA 通过期间缺陷返工数）、`qa_first_pass`（QA 是否一次通过）。撑起对账闭环的量化部分，成本≈0，不硬套 DORA 四指标。

### 2.7 v2 优化六项决策（详见《工作流优化方案》）

| 议题 | 决策 |
|---|---|
| 度量闭环 | **补**：每切片 3 个数 |
| CI | **正名**：构建验证 = "CI 等价门禁"（Reviewed 后、QA 前固定闸，状态机已锁死该顺序） |
| 分支/PR | **显式声明为有意选择**，不引入；进入多人协作时重开决策 |
| 覆盖率 | **补**：核心业务模块 ≥80%，工具/脚本/演示页不设阈值 |
| S 级 TDD | **保持强制**，不开口子 |
| 更严项 6 条（对抗审查 / QA 门禁 / 状态机 / TDD / 唯一写入者 / dry-run） | **全部保留** |

### 2.8 v2.2 决策 8：能力边界文档化 + 多入口趋同（2026-09-12 晚补充，详见《工作流优化方案》决策 8）

| 议题 | 决策 |
|---|---|
| 能力边界散落（无集中清单） | **补**：适配清单 §8「角色能力与权限边界矩阵」——全局禁做 G1–G8 + 8 角色 × 可写范围 × 绝对禁做 + 裁决优先级（用户当前指令 > Section Context 公共规则 > 各角色 SOUL > 适配清单） |
| 多入口趋同无公共规则 | **补**：Section Context 公共规则落地生效（OMB 官方分区级共享指令，用户已粘贴 v1，留档 `../../协作机制/demo-team-section-context.md`）+ 各角色 SOUL 内置入口归一条款（双保险）——单独使用任一角色时，入口行为与全组一致 |
| 知识沉淀 | OMB 学习笔记新增 05 篇（Section Context 机制 + 多入口归一四层设计 + 能力边界） |

**多入口归一四层设计**（详见 OMB学习笔记 05）：① 规则归一（Section Context + SOUL 双保险）→ ② 入口归一（业务需求→上报指挥官、只读咨询直接答、明确委派按契约）→ ③ 状态层（切片 + 状态机唯一事实源）→ ④ 验证层（QA / Reviewed 门禁不可豁免）。
**诚实边界**：OMB 无跨 bot 共享记忆，四层围堵只能降低漂移、让偏差可审计，不能保证绝对趋同（模型概率本质，§4.6 三条诚实边界）；「构造性趋同」只有单 agent 架构（如 Grok Build）才能给，本方案是「多脑 + 外部共识文件」的工程化近似。

## 三、与 Matt 单 agent skill 方式的对比

### 3.1 Matt 方式是什么（依据：`.agents/skills/ask-matt/SKILL.md` 实读）

- **单 agent 全栈**：一个 agent 从 idea 到 ship 独立完成，一条主线流程——
  `/grill-with-docs`（访谈澄清）→ 需要可运行答案时经 `/handoff` 转 `/prototype` 折返 → 多会话则 `/to-spec` → `/to-tickets`（垂直切片、blockers-first）→ `/implement`（内部驱动 `/tdd`，red-green 一次一片）→ `/code-review`（双轴）→ commit。
- **技能路由器**：`ask-matt`（人触发，`disable-model-invocation: true`），拿不准时人点名。
- **上下文卫生**：主流程一个不中断的上下文窗口；smart zone 限制；阶段边界五选一（Continue / clear / handoff / subagent / compact）。
- **on-ramps**：`/triage`（外部 bug 堆积）、`/diagnosing-bugs`（硬 bug，先建红测试再修）、`/wayfinder`（超大雾状任务，产出决策而非交付物）。
- **词汇层**：`/domain-modeling`（领域语言）、`/codebase-design`（深模块词汇），跑在所有 skill 之下。
- **人机关系**：agent **直接对用户**——grilling 访谈、quiz、质询都是 agent 与需求方之间进行。

### 3.2 相同点（我们借鉴了什么）

| Matt 概念 | Demo 对应 | 借鉴方式 |
|---|---|---|
| grill-me / grilling 对抗访谈 | 指挥官澄清 + 对抗质询（§3.1 决策表首行） | 原 skill 直接用 |
| to-spec / to-tickets 垂直切片 | Demo-Spec / Demo-Tickets 产出 prd.md / development-plan.md | 原 skill 指名调用 |
| tdd / implement（RED-GREEN） | Demo-Implement 单任务 TDD | 原 skill 指名调用 |
| code-review 双轴审查 | Demo-CodeReview 静态双轴审查 | 原 skill 指名调用 |
| diagnosing-bugs（先红后修） | 缺陷诊断委派 Demo-QA / Demo-Implement | 原 skill 指名调用 |
| wayfinder（超大任务探路） | §3.1 决策表"超大任务/方向不明"行 + 适配清单 §4.7 接缝规则 3（2026-09-12 补全：map/tickets 形态、委派契约、合流 L/M/S） | 思想采纳，落地形态已定义 |
| 技能路由器思想 | §3.1 决策表（指挥官执行路由） | 路由器职责内化 |

**结论：Matt 的 30 个技能是 Demo 执行层的主力 skill 库**（角色映射表 §3：spec/tickets/implement/codereview/build/qa 全部绑定 Matt skills），Demo 不重造轮子，直接消费 Matt 的方法论。

### 3.3 不同点

| 维度 | Matt | Demo | 不同为了什么 |
|---|---|---|---|
| 执行主体 | 单 agent 全栈，上下文连续 | 1 指挥官 + 7 专家，委派协作 | **职能隔离 + 独立校验**：写方案≠写代码≠审查≠验证；对抗审查 fresh 上下文彻底隔离调用方判断 |
| 与需求方关系 | agent 直接对用户（访谈/quiz 直接进行） | 指挥官代理需求方，子 bot 只干活；HITL 问题上抛指挥官转问 | **需求方单一接触点**；子 bot 无需求方通道，决策权集中到人闸，防止子 bot 替需求方拍板 |
| 并发控制 | 单 agent 无并发问题 | 单写入者纪律 + 状态机 | 多 bot 同时操作同一仓库时防冲突，写入可审计 |
| 上下文管理 | 靠窗口卫生（compact/handoff） | 靠 `.workflow-state.json` 外部持久化 + fresh 上下文审查 | 多 bot 之间无法共享内存，状态必须外置、就近、单一事实源 |
| 流程重量 | 轻（main flow 简洁，鼓励直接 implement） | 显式锁步（状态机不可跳步、QA S 级不豁免、Reviewed 唯一写入） | Demo 是流程演练项目，**流程重量是交付物**；生产级裁定下不追求最轻 |
| 度量 | 无显式量化闭环 | 每切片 3 个数（轻量 DORA 裁剪） | 复盘可量化，成本≈0 |

### 3.4 为什么不同（目的总结）

Matt 解决的是"**一个强 agent 高效完成工程任务**"——它的全部设计（上下文卫生、阶段边界、skill 路由）围绕单一主体的认知连续性。Demo 要的是"**生产级流程的可演练、可审计、可推广**"——于是把 Matt 的单主体拆成职能隔离的多主体：隔离带来独立校验（fresh 审查、只读 QA），代理带来单一接触点（需求方只见指挥官），状态机带来跨主体一致性（不可跳步、唯一写入者）。**拆开的主体靠文档与状态机重新粘合**——这正是 Demo 与 Matt 最本质的分野：Matt 的连续性在上下文窗口里，Demo 的连续性在仓库的产物与状态里。

## 四、与海天 product-workflow-suite 的对比

### 4.1 海天方式是什么（依据：`.agents/product-workflow-suite/` 实读）

- **19 个 product-\* 阶段 skill + 编排器**：clarify / prd / plan / technical-solution / kickoff / develop / review / test-cases / test-automation / unit-test-init / unit-test-generator / wrap-up / init / project-wiki / prototype / stitch-prototype / git-hook-init / workflow（编排）+ ask（导航，本方案未采用）。
- **全量清单**：Matt 30 个 / 海天 19 个逐项采用状态（采用 / 按需 / 未采用，含理由）见**适配清单 §3.2**（单一事实源）。汇总：Matt = 17 采用 + 12 按需 + 1 未采用；海天 = 15 采用 + 4 未采用。
- **命令约定**：Codex 环境下的人触发命令约定——连跑要用户点名工作流命令，各阶段也可单点。
- **产物命名（海天命名）**：clarify.md / prd.md / technical-solution.md / development-plan.md / start-implement.md / develop.md / test-cases.md。
- **状态机**：`.workflow-state.json`（Draft / Reviewed / Blocked / Not Applicable），看板由生成器派生、状态机是唯一源头。
- **run-mode**：through-run（连跑）/ stage-gated（逐阶段等人批）/ lite（一天小改，短 PRD + 短计划 + 两道批准门）。
- **两阶段 review**：规格符合 review + 代码质量 review；对抗审查三轴（规格 / 可判定 / 事实），**自评不算过**。
- **公共契约**：common-contracts.md（交付物核对、门禁、边界）。
- **双交付通道**：git + 软件门户（limix CLI），初始化时三选一。

### 4.2 相同点（我们借鉴了什么）

| 海天概念 | Demo 对应 | 借鉴方式 |
|---|---|---|
| 产物命名（海天命名） | `切片/<短名>/` 下 clarify.md / prd.md / technical-solution.md / development-plan.md / test-cases.md | **全盘采用**（适配清单 §4：产物命名用海天） |
| 状态机与取值 | `.workflow-state.json` Draft/Reviewed/Blocked/Not Applicable + QA-Pending/Passed/Blocked | **全盘采用**，就近放每切片 |
| run-mode 三级 | 需求分级 L/M/S 的验证侧口径（§4.5 对应关系速记） | 采用并与 L/M/S 映射 |
| 阶段门禁（过了才进下一步） | 适配清单 §4 门禁列（澄清完整才进规格、测试真绿才报完成等） | 采用并加严 |
| 对抗审查三轴 | §4.6 校验层三轴对抗（fresh 上下文） | 采用，且 Demo 用独立 bot 执行（比海天单 agent 自审更隔离） |
| lite 排除条件 | S 级排除条件（新增权限/迁移/跨仓/架构必须升 L/M） | **逐条继承**海天 lite 判定条件 |
| wrap-up 判定 | QA 环节 wrap-up 门禁 | 采用 |
| 阶段 skill 名 | 构建/QA 环节引用 product-unit-test-init / product-test-cases / product-wrap-up | 部分点名调用 |

**结论：海天贡献了 Demo 的"骨架与命名"**——流水线阶段、产物命名、状态机、run-mode、门禁语义全部以海天为底，Demo 在其上加"SDD 门禁"与"多 agent 执行"。

### 4.3 不同点

| 维度 | 海天 | Demo | 不同为了什么 |
|---|---|---|---|
| 执行环境 | Codex 环境，人触发命令约定 | OpenMausBot，无命令执行器；改为**指挥官委派指令指名 skill** + 产物标注 | 执行器不同；把"人触发"内化为"指挥官触发"，触发动作留痕可审计 |
| 触发主体 | 用户直接点命令（人对 AI） | 指挥官按决策表委派（指挥官对子 bot） | 多 agent 骨架下路由职责归指挥官，需求方仍只面对指挥官 |
| 审查执行者 | 同一 agent 内两阶段 review（仍属自审链） | 对抗审查 / 代码审查由 **Demo-CodeReview 独立 bot fresh 上下文**执行 | 把"自审"升级为"真独立审"，审查者不带方案上下文与调用方结论 |
| 状态机写入 | 各阶段 agent 写本阶段状态 | AI 只写 Draft/Blocked/Not Applicable，**Reviewed 唯一写入者=指挥官** | 人闸显式化：批准动作只有一个人能落盘，杜绝并发写冲突 |
| 流程长度 | 三段 run-mode（lite / stage-gated / through-run） | 三档 L/M/S 分级 + run-mode 双轨映射 | 需求侧与验证侧分离：分级由指挥官判定、run-mode 记录验证口径 |
| 度量 | 无显式量化闭环 | 每切片 3 个数 | 复盘可量化（v2 补） |
| 交付通道 | git + 软件门户双通道 | 仅本地 git | Demo 无远程/门户，按需求方要求 |

### 4.4 为什么不同（目的总结）

海天解决的是"**一套人触发的产品工作流，跑在单一 AI 环境里**"——命令即入口、人点即跑、agent 按契约执行。Demo 要的是"**多 bot 协作且每步可审计的生产级演练**"——于是把海天的命令入口替换为指挥官委派（留痕），把自审升级为独立 bot 审查（隔离），把人批落成唯一写入者（权责唯一），把流程长度映射为需求分级（裁剪有据）。**海天的门禁语义完整保留，执行主体从"一个 agent 听人指挥"变成"一群 bot 听指挥官指挥"**——门禁不变，组织变了；这正是 Demo 从海天学到骨架、又按自身目的改造执行层的原因。

## 五、学习借鉴总结（重点）

### 我们从 Matt 学到什么

1. **方法论，不重造**：TDD 节奏、垂直切片（tracer bullet）、先红后修的诊断、对抗访谈、深模块词汇——30 个技能直接成为执行层主力，角色映射表钉死"哪个角色用哪个"。
2. **技能路由器思想**：Matt 用 ask-matt 让人导航技能；Demo 没有命令执行器，把导航职责内化为**指挥官 + §3.1 决策表**——路由由人点变成查表可得，偏差当场可见。
3. **HITL 的价值**：Matt 的访谈/quiz/质询坚持"决策是用户的"，Demo 继承为 HITL 上抛契约——子 bot 不许替需求方拍板。

### 我们从海天学到什么

1. **骨架与命名**：11 阶段流水线、海天命名产物、`.workflow-state.json` 状态机、run-mode 三级、lite 排除条件——Demo 的流程骨架直接以海天为底。
2. **门禁语义**：每阶段"过了才进下一步"、对抗审查三轴（自评不算过）、wrap-up 收尾——这些是最值钱的部分，Demo 全盘继承并加严。
3. **裁剪哲学**：lite 的"增量小改才可轻跑"判定条件逐条继承为 S 级排除条件——轻重是**有据的裁剪**，不是随意的偷懒。

### 为什么有不同点

不同点全部服务于同一个目标：**在"生产级机制完整性"的裁定下，让多 bot 协作达到单 agent 时代无法达到的隔离度与可审计性**。

| 我们主动做的不同 | 更好的目的 |
|---|---|
| 单 agent → 多角色职能隔离 | 写方案的人不写代码、审查的人不带上下文、验证的人不碰被测代码——**独立校验**（对抗审查 fresh、QA 只读） |
| 直接对用户 → 指挥官代理 | **需求方单一接触点**；HITL 决策权集中到人闸 |
| 人触发命令 → 委派指名 + 留痕 | 每步**可审计**（决策表可对账、产物标注来源） |
| 窗口卫生 → 外部状态机 | 多 bot 间**共享事实单一来源**，不可跳步、唯一写入者 |
| 轻流程 → 显式锁步 | **流程重量是交付物**（演练项目定位），且迁移真实项目时可整体裁剪 |

一句话：**Matt 给了我们"怎么把一件事做对"的方法，海天给了我们"一套完整流程长什么样"的骨架；我们把方法装进骨架，再按多 bot 协作与生产级可审计的目的改造执行层——这就是 Demo 方案的完整来历。**

## 六、推广要点（其他项目 / 其他部门）

1. **模板 + 实值两件套**：`../团队模板/demo-team.botmrr.md`（通用核心 + 占位符）与 `../../协作机制/README.md`（项目实值，原适配清单）——新项目复用 = 生成模板 + 填实值 + 设 cwd + 对技能映射 + 跑一个真实需求验证闭环。
2. **技能库随仓库走**：cwd 直读 `.agents/`（Matt 公开技能可重新拉取；海天套件走内部渠道拷贝），不内联 OMB（超包上限且丢非 md 文件）。
3. **四层分离路径约定**（切片 / .scratch / 文档 / .agents）可直接复制；状态机就近放切片目录。
4. **先对齐定位声明**：接手新项目第一件事是确认"流程重量算不算交付物"——Demo 因演练定位选了生产级重量；真实项目需按风险裁剪（诊断记录 §六声明：度量改 DORA 全量、可引入 CI/PR、QA 门禁按团队节奏调优），**不能原样搬**。
5. **多 agent 协作三件套**（委派指名留痕 / HITL 上抛 / 单写入者纪律）是 Demo 对业界组合的增量贡献，适合任何"多个 agent 同时操作同一仓库"的场景。
6. **复盘时**：对照本总纲（方案是什么）→ 诊断记录（现状 vs 业界）→ 优化方案（决策与理由）→ 适配清单（落地细节）四件套，即可完整还原设计与演进脉络。
