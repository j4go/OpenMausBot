1v1 现状机制全景（简述）

对照对象：RFC 驱动开发（Uber/Stripe）、Google Engineering Practices、Kent Beck TDD、ThoughtWorks 技术雷达、DORA 四指标、four-eyes 评审、vertical slicing / tracer bullet、CD4P、risk-based tailoring（CMMI）。诚实边界：结构对比，非量化测量。
澄清→ 规格→ 计划→ 对抗审查→ Reviewed→ TDD 实现→ 代码审查→ 构建验证→ QA→ 测试环境部署

机制四支柱

  • 流程：澄清 → 规格 → 计划 → 对抗审查 → Reviewed → TDD → 代码审查 → 构建验证 → QA → 部署
  • 分级：L/M/S（§4.5）——分级是流程选择、不是门禁豁免
  • 路由：场景 → skill → 角色决策表（§3.1）
  • 约束链：规则查表 → 契约留痕 → 校验独立 → 门禁人闸（§4.6）
  • 交付物：切片/<短名>/ 下 clarify.md / prd.md / technical-solution.md / development-plan.md / test-cases.md / deployment-process.md + .workflow-state.json

#机制主流对应更严在哪
1对抗审查（fresh 上下文，三轴）four-eyes 独立评审fresh 上下文彻底隔离调用方判断，多数团队评审带上下文
2QA 独立门禁，S 级不豁免DoD + 独立 QAS 级快速验证仍保留 QA 判定
3状态机不可跳步流程门禁主流倾向最轻流程，我们显式锁步
4TDD 强制Kent Beck TDD（业界实际采纳率低）主流多数为 test-after
5Reviewed 唯一写入者避免并发写冲突单写入者约束显式化
6部署默认 dry-run + runbookCD4P 变更管理保守侧：无 runbook 不部署

3缺漏项 4 条（可改进 · v2 讨论对象）

#缺漏主流实践影响可选改进方向
1度量闭环缺失（最大）DORA 四指标只有定性对账，无量化数据闭环轻量度量表：每切片记录周期/缺陷数/QA 结果
2CI 自动化未定义push 即 CI构建验证靠 bot 手动触发定义 CI 等价门禁
3分支/PR 策略未定义trunk-based + 短命分支 + PR直接 commit 主分支显式声明为有意选择，或引入分支
4测试覆盖率门禁未定义按模块 80% 或风险分级TDD 有、阈值无定义覆盖率阈值策略（按风险分级）
⚠️ 张力点：流程重量 vs 主流"最轻流程"。Demo 是流程演练项目，流程重量本身就是交付物；若迁移真实生产项目需按风险裁剪、不能原样搬——v2 保持并显式声明此立场。

4v2 决策（六项 + v2.2 决策 8，2026-09-12 需求方逐条确认）

总基调：Demo 需求与功能是演示级，但工作流、skills、交付物、agent 协作均为生产级要求；优化目标是"生产级机制的完整性"，不是"放松流程"。
#议题决策类型一句话理由
1度量闭环（缺漏 1）补：每切片 .workflow-state.json 记 3 个数——澄清→Reviewed 前置时间 / 实现→QA 缺陷返工数 / QA 一次通过新增机制撑起对账闭环的量化部分，成本≈0，不硬套 DORA
2CI（缺漏 2）正名：构建验证 = "CI 等价门禁"，Reviewed 后、QA 前固定闸正名现有机制已被状态机锁死，只差显式命名
3分支/PR（缺漏 3）显式声明为有意选择，不引入；多人协作时重开决策决策记录单人单机 + 流程内双审查已是替代品
4覆盖率（缺漏 4）补：核心业务模块 ≥80%，工具/脚本/演示页不设阈值新增机制TDD 管"有测试"，阈值管"测到关键处"
5TDD 在 S 级保持强制，不开口子裁定确认需求方裁定：需要严谨测试就不该归 S 级
6更严项 6 条全部保留，不动裁定确认生产级裁定下流程重量是交付物
7能力边界 + 多入口趋同（v2.2 决策 8）补：适配清单 §8 角色能力与权限边界矩阵（G1–G8 + 8 角色×可写范围×绝对禁做 + 裁决优先级）；Section Context 公共规则落地生效（用户已粘贴）+ 各 SOUL 入口归一条款（双保险）新增机制边界集中可审计；任意角色单独使用时行为与全组一致
🗣️ S 级 TDD 裁定原文（需求方）："S 级别的 tdd 就足够了，不用那么测试；如果需要比较严谨的测试，就不应该归类为 S 级。" 推论：分级本身承担风险裁剪——需严谨测试的需求按定义归 M/L，而不是在 S 级放松测试要求。
