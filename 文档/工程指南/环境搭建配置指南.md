# Agent 研发环境搭建配置指南

> 以 Demo 团队（`E:\Demo`）为落地实例，完整记录一套「OMB 团队角色 + 项目技能库 + 项目规范」三层研发环境的搭建方法。
> 目标读者：想搭建属于自己 agent 开发环境的同事。按第 6 章从零搭建步骤操作，即可复刻一套同样配置。
> 本文所有"实值"均来自本仓库已验证文件（README.md / 协作机制（原适配清单）/ demo-team.botmrr.md / OMB学习笔记 01-06 / 切片产物 / application.yml）。

## 1. 这套环境的整体架构

### 1.2 三条核心设计思想

| # | 思想 | 落地方式 | 好处 |
|---|---|---|---|
| 1 | **团队定义与项目解耦** | 角色 SOUL 提炼成"通用核心 + 占位符"，机器路径/项目规范外置到《协作机制/README.md》（原适配清单） | 换项目不用重建 8 个 agent，几分钟导入副本即用 |
| 2 | **技能 cwd 直读而非导入** | bot 的 working folder 指到项目目录，其文件工具直接读 `.agents/` | 49 个 skill 超团队包 20 个上限；套件含非 md 资源，内联会破坏 |
| 3 | **产物命名用海天，门禁用 SDD** | 切片产物 `clarify.md / prd.md / ...`（海天），状态机 `Draft → Reviewed → QA-*`（SDD） | 两套流程同构（Draft/Reviewed/Blocked/Not Applicable），不打架 |

## 2. 第一层：项目规范与流程机制

### 2.1 AGENTS.md 双层规范

Agent 平台按层级读取规范文件，上层约定全局纪律、下层约定项目纪律：

- **全局层**（如 `~/.pi/agent/AGENTS.md`）：优先级与沟通、自主推进、授权边界（Ask first）、修改与保护、验证与交付、环境约定。跨项目通用。
- **项目层**（`<项目>/AGENTS.md`）：项目定位、流程纪律（需求流程 / 分级 / 状态机 / 产物命名 / 委派纪律）、构建与验证命令、领域规则（工单状态机）、安全与边界。

Demo 项目级 AGENTS.md 的骨架（新项目可直接改）：

```markdown
# AGENTS.md —— <项目> 规范

## 项目定位
<一句话：做什么、验证什么机制、技术栈>

## 流程纪律（所有角色必须遵守）
- 需求流程：澄清 → 规格 → 任务计划 → 对抗审查 → Reviewed（人批）→ TDD 实现 → 代码审查 → 构建 → QA 判定 → 部署(dry-run)
- 需求分级：澄清阶段指挥官先判定 lane（L / M / S），按分级裁剪流程长度（见协作机制/01-需求分级.md）
- 状态机：.workflow-state.json 中 AI 只写 Draft/Blocked/Not Applicable；Reviewed 只能指挥官写
- 产物命名（切片/<需求短名>/）：clarify.md / prd.md / technical-solution.md / development-plan.md / test-cases.md
- 委派纪律：先委派规格和计划，再委派单一实现者；不让两个写入角色同时修改工作区
- 每次委派必须说明：输入、输出文件、写入范围、验证命令
- 无测试部署 runbook 和本轮明确批准时，部署角色只能 dry-run

## 构建与验证
<具体的命令，如 mvn test / npm run build>

## 领域规则
<业务规则，如工单状态机、错误码约定>

## 安全与边界
- <凭据文件> 为禁读边界；部署、push、持久化迁移默认需明确批准
```

### 2.2 SDD 流程链

完整流程（L 级全链，M/S 按 §2.4 裁剪）：

```
需求澄清 → 规格 → 任务计划 → 对抗审查（CodeReview fresh 上下文审查方案，人批前跑）
→ 你批 Reviewed → TDD 实现 → 代码审查 → 构建和验证 → 本地运行
→ QA 验证（计划层判定 + wrap-up 验证门禁）→ 测试环境部署（默认 dry-run）
```

两道最贵的闸：**Reviewed 人批**（只能指挥官写）、**QA 判定**（QA-Pending → QA-Passed / QA-Blocked）。

### 2.3 状态机与门禁（SDD ↔ 海天产物 ↔ 状态机对照）

| SDD 阶段 | 海天阶段/产物 | 状态机取值 | 门禁 |
|---|---|---|---|
| 需求澄清 | `clarify.md` | Draft | 澄清完整才能进规格 |
| 规格 | `prd.md`（可选 `prototype.html`） | Draft | 三轴对抗审查通过 |
| **Reviewed（人批）** | — | **Reviewed（只能指挥官写）** | **人批准** |
| 任务计划 | `technical-solution.md`、`development-plan.md` | Draft | 计划含验证命令与写入范围 |
| TDD 实现 | 代码 + 单测 | Draft/Blocked | 测试真绿才报完成 |
| 代码审查 | 代码 diff | Draft | 静态双轴审查 |
| 构建与验证 | 构建产物 + 健康检查 | Draft | 真实 PASS 输出 |
| QA 验证 | `test-cases.md`、wrap-up | QA-Pending → QA-Passed / QA-Blocked | Gate Function |
| 测试环境部署 | 部署 + 冒烟 | — | dry-run + 双重批准 |

状态机实值示例（`切片/工单评论/.workflow-state.json`）：8 个阶段（clarify/prd/plan/adversarial-review/implement/review/build/qa/deploy）各有 status / updated_at / note；`lane: M`、`run_mode: stage-gated`、`current_stage: deploy`。

### 2.4 需求分级 L / M / S（流程长度的横向裁剪）

> 分级是**流程选择，不是门禁豁免**——Reviewed 人批与 QA 判定各级保留。判定发生在指挥官澄清阶段。

| 级别 | 典型需求 | 流程 | QA run-mode | 产物与 skill |
|---|---|---|---|---|
| **L 大型/从 0** | 新功能、跨层改动 | 完整流水线，全部门禁 | through-run / stage-gated | 全产物集 + 全链 skill |
| **M 中型/单层** | 模块内增强、bug 修复 | 澄清 →（轻量计划）→ 对抗审查 → Reviewed → TDD → Review → QA | stage-gated | 精简规格/计划，保留对抗审查与 QA |
| **S 小型/快速** | 文案、样式、单点修复、文档 | 直接委派 Implement（或指挥官直接改）→ 快速验证 | lite | 短 prd + 短 plan + 验证证据 |

降级 S 的排除条件（不满足任一条不得降级）：涉及新权限模型 / 敏感数据 / schema 迁移 / 跨仓契约 / 架构边界时必须走 L 或 M；fog（不确定高）时不降级。分级结果写入 `.workflow-state.json` 的 `run_mode`。

### 2.5 委派纪律与单一写入者

- 先委派**规格和计划**，再委派**单一实现者**；实现后委派只读 Review、构建和验证。
- **不让两个写入角色同时修改工作区**（写入角色互斥）。
- 每次委派必须说明：输入、输出文件、写入范围、验证命令。
- 只读角色（CodeReview / QA）不写被测代码；QA 公共测试资产互斥（同一时刻只允许一个写入角色跑 E2E）。

### 2.6 需求切片目录与产物命名

每个需求一个切片目录：`切片/<需求短名>/`，放海天命名产物：

```
切片/工单评论/
├── .workflow-state.json    # 状态机（见 §2.3）
├── clarify.md              # 需求澄清（范围/非目标/默认决策/分级判定）
├── prd.md                  # 规格（含验收标准 AC-N）
├── technical-solution.md   # 技术方案（L 必产 / M 可选，决策可并入 prd+plan）
├── development-plan.md     # 任务计划（TASK-N，含验证命令与写入范围）
├── test-cases.md           # 测试用例（M 级以上必产，QA 写：自动化 AC 一行映射 + 非自动化用例完整写）
└── deployment-process.md   # 部署过程记录（dry-run 演练沉淀，含冒烟计划与真部署前置清单）
```

`.scratch/<feature>/` 是 Matt 体系的本地 markdown issue tracker（票 + 缺陷 triage），不依赖 GitHub；**纯过程区**（日志、临时脚本、演练草稿），gitignore，整目录可随时删除——验证证据（build-verification.md / qa-verification.md / 截图）直接落 `切片/<需求短名>/` 入库。

### 2.7 QA 验证门禁（Gate Function）

QA 是独立动态验证角色（只读），两个判定层：

1. **计划层判定**：按 run-mode 分级决定验证范围（lite / stage-gated / through-run；改 UI 才含 E2E）；
2. **wrap-up 验证门禁**：`IDENTIFY（列清单）→ RUN（只认本轮新鲜跑出来的证据）→ READ（读结果）→ VERIFY（对照验收标准）→ ONLY THEN（全部过关才宣布完成）`。

铁律："之前跑过 / 应该能过"不算证据；没有本轮新鲜验证输出不得声称通过；不得放宽超时/重试/阈值换取通过。

### 2.8 状态看板广播边界（2026-09-11 用户裁定）

看板房间 `demo-status-board`（仅指挥官为成员，mentions 默认应答）**只广播真正的项目需求**（改代码/修 bug 等业务逻辑任务）的阶段状态行：

```
格式：[需求] 阶段 → 结果 (commit/链接)
⚠️ 需要你介入的点（Reviewed 批准 / QA 阻塞裁决 / 部署批准）会显式标注
对话型/文档型/咨询型任务不广播，不发初始化/元消息
```

### 3.2 为什么 cwd 直读而不是导入 OMB

skill 进入 OMB 有三条通道（源码核实，见笔记 04）：

| 通道 | 机制 | 上限/限制 | 适用 |
|---|---|---|---|
| 团队包内联 | BotMRR `package.skills.entries` | **≤20 个/包**；每 ≤256KB；source 拒绝绝对路径；导入后默认 disabled | 少量开箱即用纪律 skill |
| GitHub 导入 | bot 设置页 Import，只接受 owner/repo、github.com URL、raw SKILL.md | 每包 ≤30；仅 markdown | 从公开仓库按需拉取 |
| skill_manage 创建 | 指挥官工具 → 用户批准卡 | — | 沉淀 OMB 级通用纪律 |

Demo 的 49 个 skills（30+19）超 20 上限，且海天套件依赖非 md 资源（scripts/ 等），不能内联。**决策：项目技能库随仓库走，角色 cwd 指向项目后直接读取**；模板 SOUL 只写"技能取用规则 + 映射表位置"，不内联 skills。

### 3.3 角色 ↔ skill 映射表（协作机制/02-场景决策表.md §3，实值）

"怎么做"委托给 skill，"何时委派、门禁是什么"留在 SOUL：

| 角色 | Matt skills | 海天 skills |
|---|---|---|
| 指挥官 commander | wayfinder, grilling, to-questionnaire | product-workflow |
| 规格 Spec | to-spec, research, prototype | product-clarify, product-prd, product-kickoff |
| 计划 Tickets | to-tickets, triage | product-plan, product-technical-solution |
| 实现 Implement | tdd, implement, resolving-merge-conflicts | product-develop, product-unit-test-generator, product-unit-test-init |
| 审查 CodeReview | code-review, grilling, codebase-design, domain-modeling | product-review |
| 构建 Build | setup-pre-commit, setup-matt-pocock-skills | product-git-hook-init, product-init |
| QA | diagnosing-bugs | product-test-automation, product-test-cases, product-wrap-up |
| 部署 Deploy | （无直接对应） | （无直接对应，部署是角色纪律而非 skill） |

> 场景决策（什么场景指名调什么 skill）见协作机制/02-场景决策表.md；合理性约束链与对账闭环见协作机制/04-约束链与对账.md；

### 3.4 给别人的移植建议

- 自己的项目直接复用 `.agents/` 目录结构（Matt skills 来自公开仓库可重新拉取；海天套件是内部交付物，走内部渠道拷贝）；
- 新增技能优先放**项目技能库**（cwd 直读），只有跨项目通用纪律才考虑 OMB 级导入。

## 4. 第三层：OMB 团队角色配置

### 4.1 8 角色一览（key / name / title / 职责）

| key | name | title | 核心职责 |
|---|---|---|---|
| commander | 指挥官 | Chief of Staff · SDD 指挥官 | 全流程协调；**Reviewed 唯一写入者**；批准与交付门禁 |
| spec | 产品经理Spec | 规格专家 | 澄清→规格产物（clarify.md / prd.md），验收标准明确 |
| tickets | 技术经理Tickets | 计划与缺陷管理专家 | 任务拆解（development-plan.md）；缺陷 triage 分级闭环 |
| implement | 开发工程师Implement | TDD 实现者 | 单任务 TDD（RED-GREEN-REFACTOR），如实报告 |
| codereview | 代码审查CodeReview | 代码审查与对抗审查专家 | 人批前 fresh 对抗审查（三轴+人机两句）+ 实现后静态双轴审查 |
| build | 本地构建Build | 本地开发与构建验证专家 | 起栈、构建、健康检查，QA 前置 |
| qa | QA验证 | 独立动态验证专家 | 计划层判定 + wrap-up 门禁（Gate Function），只读 |
| deploy | 测试服部署Deploy | 测试环境部署专家 | 打包、传输、deploy 与冒烟；**默认 dry-run，双重批准** |

### 4.2 SOUL 编写要点（以指挥官为例解剖）

一份合格的角色 SOUL 包含 6 个固定板块（实值来自 demo-team.botmrr.md；非指挥官角色另有【6. 入口归一】）：

```markdown
你是 {{PROJECT_NAME}} 的研发流程指挥官（Chief of Staff）。

【1. 定位一句话】
先澄清需求、范围、非目标和验收标准；读取项目规范文件（AGENTS.md / CONTEXT.md 等，清单见 {{ADAPT_FILE}}）。

【2. 流程与门禁】
流程必须是：需求澄清 → 规格 → 任务计划 → 对抗审查（CodeReview 以 fresh 上下文审查方案，在你批准之前跑）
→ 你批 Reviewed → TDD 实现 → 代码审查 → 构建和验证 → 本地运行 → QA 验证 → 测试环境部署。
状态机写在 .workflow-state.json，AI 只写 Draft/Blocked/Not Applicable，Reviewed 只能你写；QA 环节取值 QA-Pending → QA-Passed / QA-Blocked。

【3. 分级】
澄清阶段先判定需求分级（L/M/S，规则见 {{ADAPT_FILE}}）：L 全链、M 简化规格与计划但保留对抗审查与 Reviewed、S 直接委派快速验证。
分级是流程选择，不是门禁豁免。

【4. 委派纪律】
先委派规格和计划，再委派单一实现者。实现后委派只读 Review、构建和验证。
不要让两个写入角色同时修改 {{PROJECT_DIR}}。每次委派必须说明输入、输出文件、写入范围和验证命令。
没有测试部署 runbook 和本轮明确批准时，部署角色只能 dry-run。

【5. 安全与边界】
技能取用：项目技能库在 {{SKILLS_DIR}}（映射见 {{ADAPT_FILE}}）；拿不准走哪步时查 {{ADAPT_FILE}} §3.1 决策表。
状态看板只广播真正的项目需求；对话型/文档型/咨询型任务不广播。
不要读取或输出项目的凭据/密钥文件（路径见 {{ADAPT_FILE}}）。不要自行扩大需求、添加依赖、执行持久化迁移、push、发布或生产部署。

【6. 入口归一】（非指挥官角色；指挥官即入口，不需要）
收到业务需求（改代码 / 修 bug / 新增功能 / 任何要写 {{PROJECT_DIR}} 仓库的工作）→ 上报指挥官，由指挥官走 SDD 流程分级分派；
不要自行开工、不要自行委托其他 bot。收到只读咨询（问机制 / 问现状 / 问文档 / 问仓库内容）→ 直接回答，不用上报。
收到指挥官明确委派 → 按委派执行。只读角色（QA / CodeReview）追加：收到写仓库请求（含用户直接指示）→ 说明只读边界并上报指挥官，不自行写入。
```

角色 SOUL 的差异化重点：

- **spec**：只写规格产物，不碰业务源码/测试/构建/凭据；需求不清楚停止并向指挥官提问，不猜测。
- **tickets**：任务必须含精确路径、目的、前置依赖、测试先行步骤、验证命令、写入范围、完成定义；只写计划与缺陷文件。
- **implement**：一次一个已批准任务，不重新设计需求、不扩大范围；完成前报告实际测试/格式化/验证命令输出。
- **codereview**：只读；所有发现必须给出严重程度、文件/行号、证据、最小修复建议；无真实验证输出不得声称通过。
- **build**：不自动杀进程、不连远程测试服、不把构建成功当测试成功、不仅看退出码（必须检查 PASS/FAIL 输出）。
- **qa**：只读验证；Gate Function（§2.7）；缺陷分级回流（真缺陷→Tickets、环境/栈→Build、flaky→按 Runbook 归类、琐碎→直连 Implement）。
- **deploy**：默认只 dry-run、证据检查和命令准备；不索要/保存/输出密码；不用 sshpass；文件传输前和 deploy 执行前都需要用户明确批准；不把生成命令当已执行证据。

### 4.3 三层分离提炼法（模板必须与项目解耦）

直接导出 SOUL 会带进机器/项目硬编码，按生命周期分三层处理（实测占比）：

| 层 | 占比 | 内容 | 模板处理 |
|---|---|---|---|
| ① 通用核心 | ~60% | SDD 流程骨架、状态机约定、单一写入者、Gate Function、TDD、缺陷 triage | 原样保留 |
| ② 项目规范 | ~25% | AGENTS.md 引用、切片路径、验证命令引用、skill 引用 | 改占位符（`{{PROJECT_NAME}}` / `{{PROJECT_DIR}}` / `{{SLICE_DIR}}` / `{{SKILLS_DIR}}` / `{{ADAPT_FILE}}` / `{{VERIFY_SKILL}}`），实值外置到协作机制/README.md（原适配清单） |
| ③ 机器/环境硬编码 | ~15% | `E:\...` 路径、`.bat` 脚本、内网地址、tag 格式、凭据文件路径 | **全部删除**，只保留"见 {{ADAPT_FILE}}"式引用 |

**判断标准**：模板里不允许出现任何"这台机器/这个仓库"才有的字符串。

### 4.4 人批门禁设计（最贵的一道闸）

- Reviewed 状态**只能指挥官写**，其他角色（包括 Spec/Implement）不得自写 Reviewed——实现者 SOUL 明示"不自行写 Reviewed（Reviewed 只能人写）"；
- 对抗审查在**人批之前**跑：CodeReview 以 fresh 上下文（不继承写稿会话）审方案文档，按三轴（规格完整 / 可判定 / 事实准确）+ 人机两句（没参会的人能否读懂、干净会话只喂文档能否开干）；
- 需求方在每个阶段产物上逐条表态（接受默认或改判），如 clarify 的 §9 默认决策记录。

### 4.5 导入后必做（模板不携带运行时状态）

团队包是纯定义：**不含 cwd、记忆、历史、凭据、模型选择、权限字段**。导入后逐角色设置：

1. **cwd（working folder）** → 项目目录（不随模板携带，必须手工设）；
2. **模型选择**（每个 bot 指定所用模型）；
3. 按协作机制/02-场景决策表.md 确认技能映射就位（cwd 直读 `.agents` 即可）；
4. 检查 routine（导入后一律 paused，需用户手动启用）。

## 5. 团队模板 BotMRR：制作与导入

### 5.1 文件结构（两部分缺一不可）

```markdown
---
botmrr: 1                    # YAML frontmatter：版本标记 + 完整包定义
id: demo-team                # 小写 slug，^[a-z0-9][a-z0-9-]*$
release: 1.1.0               # 语义化版本
name / tagline / summary / category / author / license
outcomes: [...]              # 1-12 条
setupMinutes: 15
requirements: { apps: [], capabilities: [...] }
agents:                      # 1-200 个
  - key: commander           # key 规则 ^[a-z0-9][a-z0-9_-]*$
    name: 指挥官
    title: Chief of Staff · SDD 指挥官
    description: ...         # ≤4000 字节
    soul: |                  # 块标量，≤24000 字节
      （SOUL 全文，提炼版）
    appearance:
      color: pink            # 限 10 色：green/blue/red/orange/purple/cyan/pink/yellow/teal/coral
      mascotBody: drop
chiefOfStaff: commander      # 必须是某 agent 的 key
rooms:                       # 可选，最多 30
  - key: demo-status-board
    name: Demo 状态看板
    members: [commander]     # 必须是 agent key
    bulletin: |              # ≤12000
      ...
    defaultResponder: { kind: mentions }   # agent(须是成员)/everyone/mentions
routines:                    # 可选
  - key: error-log-watch
    agent: commander         # 必须是 agent key
    prompt: |                # 巡检指令（triage 分级 → 标准 SDD 流程）
    schedule: { type: interval, everyMinutes: 60 }
    enabledAfterInstall: false   # 必须 false，导入后默认暂停
---
（空行）
# <团队名>                  # Markdown 正文，必须含 7 个节（缺一不可）：
## Activation              ## Mission    ## Outcomes  ## Connections
## Team                    ## Chief of Staff        ## Completion rule
```

### 5.2 校验规则与自检脚本

源码 `server/bot-package.ts` 用 zod 严格校验，手工写模板前对照自检：

- frontmatter 必须是合法 YAML，`botmrr: 1` 为版本标记；
- 正文必须含 7 个必需节，否则报 "missing its X section"；
- agent/room/routine 的 key 唯一且匹配 `^[a-z0-9][a-z0-9_-]*$`；
- 引用完整性：chiefOfStaff 必须是 agent key；room 成员必须是 agent key；defaultResponder 为 agent 时必须是该 room 成员；routine 的 agent 必须是 agent key；
- soul ≤ 24000 字节、description ≤ 4000、name ≤ 100、title ≤ 200；
- 颜色限 10 枚举色；routines 的 `enabledAfterInstall` 必须为 `false`；
- **权限字段被剥离**：approvalMode、autoApprove 等不进包（防 privilege smuggling）；ids、grants、credentials、paths（含 cwd）、model selections、runtime state 一律不过包边界。

Demo 的自检脚本：`文档/团队模板/_validate_botmrr.py`（模拟 parseBotPackage 全部规则，`VALIDATION PASSED`）。新写模板建议同样验证后再导入。

### 5.3 导入三步（新项目落地）

1. **导入**：侧边栏 `+` → Teams → **Import**（选本地 `.md`）或 **From a folder**（项目模式：团队包 + 指定目录 + 自动开房间，一步到位）。同名角色显示为 "New copy of X"，**不覆盖**现有角色；
2. **适配**：按《协作机制/README.md》§1（原适配清单，2026-09-13 迁入机制库）把占位符替换成新项目实值；逐角色设 **cwd** 和**模型选择**；
3. **开工**：指挥官自动成为 Chief of Staff，流程照常。

### 5.4 版本与导出坑（踩过的大坑）

- **新版 OMB 没有"导出团队"按钮**（旧版 "Export all bots" 已移除；服务端 `package-export.ts` 仍有 `createBotPackageExport()`，但无 UI）。制作模板 = 手工编写 BotMRR Markdown（可控、可审阅、随仓库版本化）或走 API。
- **备份 ≠ 移植**：`Settings → Workspace Backup` 导出的是加密 `.ombbackup`（整工作区快照，含对话/凭据，恢复覆盖），是备份不是团队模板。
- **版本前提**：项目模式导入（`mode=project`）需要 OMB ≥ 2026-08-21（PR #316）。UI 能看到 **From a folder** tab 即新版。
- **导入副本是干净的**：无记忆/历史/已连接 app 授权——特性（模板纯净），也意味着新 bot 要重设 cwd 和模型。

## 7. 安全与凭据边界

### 7.1 禁读边界

`/.local-credentials.env` 等敏感文件为**禁读边界**：所有角色（含指挥官）不得打开、读取、搜索、索引、摘要或展示内容，只允许元数据检查。gitignore 保证不入库：

```gitignore
# 敏感文件（禁读边界）
/.local-credentials.env
```

### 7.2 凭据外置注入模式（Spring 实值）

应用不落明文凭据，按环境注入：

```yaml
# backend/src/main/resources/application.yml
spring:
  config:
    # 本地凭据从仓库根 .local-credentials.env 注入（properties 格式 DB_USERNAME=xxx / DB_PASSWORD=xxx）
    # [.properties] 是格式提示：.env 扩展名不在 Spring 原生支持列表，必须显式声明按 properties 解析
    import: optional:file:../.local-credentials.env[.properties]
  datasource:
    url: jdbc:mysql://localhost:3306/demo?...
    username: ${DB_USERNAME}    # 占位符无默认值 → 无凭据来源时启动即报错（fail fast）
    password: ${DB_PASSWORD}    # 而非带着空密码悄悄连库
  jpa:
    hibernate:
      ddl-auto: update          # 重启不丢数据；首次启动自动建表
    open-in-view: false
```

测试服不依赖本文件：由部署环境注入 `DB_USERNAME` / `DB_PASSWORD` 环境变量（优先级高于文件）。测试用 H2 内存库（`src/test/resources/application.yml`，`jdbc:h2:mem:tickets-test`，`ddl-auto: create-drop`），不依赖本地 MySQL。

**已知坑**：`.env` 不是 Spring 原生配置扩展名，config import 必须带 `[.properties]` 格式提示，否则 optional 静默吞错、占位符原样传 JDBC 报 Access denied。

### 7.3 部署 dry-run 纪律

- 无测试部署 runbook 和本轮明确批准时，部署角色只能 **dry-run**（证据检查 + 命令准备，零真实动作）；
- deploy 角色：不索要/保存/输出密码、不用 sshpass、文件传输前与 deploy 执行前都需用户明确批准、不把生成命令当已执行证据、失败先停止收集输出不自作主张回滚；
- 真部署前置清单与冒烟计划示例：`切片/工单评论/deployment-process.md`（打包链路已实测：backend fat jar + frontend dist；传输/部署链路未建立则如实标注）。

## 8. 踩坑清单（别人不用再踩）

| # | 坑 | 解法 |
|---|---|---|
| 1 | `.env` 扩展名不被 Spring 识别，optional import 静默吞错 | `import: optional:file:...env[.properties]` 显式格式提示；占位符无默认值 → fail fast |
| 2 | 新版 OMB 找不到"导出团队"按钮 | 没有 UI；用手工 BotMRR Markdown 或 API；`.ombbackup` 是备份不是模板 |
| 3 | 团队包不携带 cwd / 模型 / 记忆 / 凭据 | 导入后逐角色重设 cwd 与模型（特性：模板纯净） |
| 4 | 团队包 skills ≤ 20 个、只带 markdown | 项目技能库走 cwd 直读，不内联 |
| 5 | 项目模式导入需要 OMB ≥ 2026-08-21（PR #316） | 看 UI 有没有 **From a folder** tab |
| 6 | routine 导入后处于启用状态的风险 | BotMRR 强制 `enabledAfterInstall: false`，导入后一律 paused |
| 7 | 角色自写 Reviewed 破坏门禁 | SOUL 明示 Reviewed 只能指挥官写；AI 只写 Draft/Blocked/Not Applicable |
| 8 | 对抗审查用写稿会话的上下文 | CodeReview 必须以 fresh 上下文审查方案文档 |
| 9 | 把构建成功当测试成功 / 只看退出码 | 验证必须检查真实 PASS/FAIL 输出；QA Gate Function 只认本轮新鲜证据 |
| 10 | 看板刷屏 | 只广播真正的项目需求状态行；文档/对话/咨询型任务不推 |
