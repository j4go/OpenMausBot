Agent 研发环境搭建配置指南

以 Demo 团队（E:\Demo）为落地实例，完整记录「OMB 团队角色 + 项目技能库 + 项目规范」三层研发环境的搭建方法。目标读者：想搭建属于自己 agent 开发环境的同事——按第 6 章从零搭建步骤操作即可复刻。

1这套环境的整体架构：三层组成

团队定义与项目解耦——真正指向项目的只有每个 bot 的 cwd 指针。
①

团队角色层（OMB） 8 个 bot

指挥官 / Spec / Tickets / Implement / CodeReview / Build / QA / Deploy——定义存全局（bots.json + SOUL.md），换项目只改 cwd 指针。
②

项目技能库层（.agents/，随仓库版本化） 49 个 skill

skills/ = Matt 工程 skills（30 个）· product-workflow-suite/ = 海天产品工作流套件（19 个）。角色 cwd 指向项目后直接读取，无需导入 OMB。
③

项目规范层（仓库内文档）

AGENTS.md（项目级工作约定）· 协作机制/（机制事实源，原适配清单 09-13 迁入）· 文档/机制与方案/（团队机制方案沉淀）· 文档/团队模板/（botmrr 模板 + 自检脚本）· 切片/（需求产物，海天命名）· .scratch/（纯过程区，整目录可随时删除）。
#核心设计思想落地方式好处
1团队定义与项目解耦角色 SOUL 提炼成"通用核心 + 占位符"，机器路径/项目规范外置到适配清单换项目不用重建 8 个 agent，几分钟导入副本即用
2技能 cwd 直读而非导入bot 的 working folder 指到项目目录，其文件工具直接读 .agents/49 个 skill 超团队包 20 个上限；套件含非 md 资源，内联会破坏
3产物命名用海天，门禁用 SDD切片产物 clarify.md / prd.md / …（海天），状态机 Draft → Reviewed → QA-*（SDD）两套流程同构（Draft/Reviewed/Blocked/Not Applicable），不打架

2SDD 流程链 · 状态机 · 门禁

两道最贵的闸：Reviewed 人批（只能指挥官写）、QA 判定（QA-Pending → QA-Passed / QA-Blocked）。
SDD 阶段海天阶段/产物状态机取值门禁
需求澄清clarify.mdDraft澄清完整才能进规格
规格prd.md（可选 prototype.html）Draft三轴对抗审查通过
Reviewed（人批）—Reviewed（只能指挥官写）人批准
任务计划technical-solution.md、development-plan.mdDraft计划含验证命令与写入范围
TDD 实现代码 + 单测Draft/Blocked测试真绿才报完成
代码审查代码 diffDraft静态双轴审查
构建与验证构建产物 + 健康检查DraftCI 等价门禁真实 PASS 输出
QA 验证test-cases.md、wrap-upQA-Pending → Passed / BlockedGate Function
测试环境部署部署 + 冒烟—dry-run + 双重批准
⛔ 需求分级 L / M / S 降级排除条件：涉及新权限模型 / 敏感数据 / schema 迁移 / 跨仓契约 / 架构边界时必须走 L 或 M；fog（不确定高）时不降级。分级写入 .workflow-state.json 的 run_mode（lite / stage-gated / through-run）。

3项目技能库：为什么 cwd 直读而不是导入 OMB

skill 进入 OMB 有三条通道（源码核实）；Demo 的 49 个 skills 超 20 上限，且海天套件依赖非 md 资源（scripts/ 等），不能内联。
通道机制上限/限制适用
团队包内联BotMRR package.skills.entries（完整 SKILL.md 文本）≤20 个/包；每 ≤256KB；source 拒绝绝对路径；导入后默认 disabled少量开箱即用纪律 skill
GitHub 导入bot 设置页 Import，只接受 owner/repo、github.com URL、raw SKILL.md每包 ≤30；仅 markdown从公开仓库按需拉取
skill_manage 创建指挥官工具 → 用户批准卡—沉淀 OMB 级通用纪律
✅ 决策：项目技能库随仓库走，角色 cwd 指向项目后直接读取；模板 SOUL 只写"技能取用规则 + 映射表位置"，不内联 skills。移植建议：新项目直接复用 .agents/ 结构（Matt 公开技能可重新拉取；海天套件走内部渠道拷贝）。

SOUL 编写要点（一份合格的角色 SOUL 含 6 个固定板块）

板块内容
① 定位一句话先澄清需求、范围、非目标、验收标准；读取项目规范文件（AGENTS.md / CONTEXT.md 等）
② 流程与门禁流程必须是：澄清 → 规格 → 计划 → 对抗审查（fresh）→ Reviewed → TDD → 代码审查 → 构建验证 → 本地运行 → QA → 测试环境部署；状态机 AI 只写 Draft/Blocked/Not Applicable，Reviewed 只能指挥官写
③ 分级澄清阶段先判定需求分级（L/M/S）；分级是流程选择，不是门禁豁免
④ 委派纪律先委派规格和计划，再委派单一实现者；不让两个写入角色同时改项目目录；每次委派说明输入/输出/写入范围/验证命令；无 runbook + 明确批准时部署只能 dry-run
⑤ 安全与边界技能取用规则 + 映射表位置；看板只广播真正的项目需求；不读凭据/密钥文件；不自行扩大需求、添加依赖、迁移、push、发布、生产部署
⑥ 入口归一（非指挥官角色；指挥官即入口）收到业务需求→上报指挥官分级分派，不自行开工/委托；只读咨询直接答；明确委派按契约执行；只读角色（QA/CodeReview）追加：收到写仓库请求（含用户直接指示）→说明边界并上报，不自行写入。与 Section Context 公共规则同源（双保险）

三层分离提炼法（模板必须与项目解耦）

~60%

① 通用核心

  • SDD 流程骨架、状态机约定、单一写入者、Gate Function、TDD、缺陷 triage
  • 原样保留
~25%

② 项目规范

  • AGENTS.md 引用、切片路径、验证命令、skill 引用
  • 改占位符（{{PROJECT_NAME}} 等），实值外置到适配清单
~15%

③ 机器/环境硬编码

  • E:\ 路径、.bat 脚本、内网地址、tag 格式、凭据文件路径
  • 全部删除，只保留"见 {{ADAPT_FILE}}"式引用
⭐ 判断标准：模板里不允许出现任何"这台机器 / 这个仓库"才有的字符串。人批门禁设计：Reviewed 只能指挥官写；对抗审查在人批之前跑（fresh 上下文，不继承写稿会话）；需求方在每个阶段产物上逐条表态。

5团队模板 BotMRR：制作、校验、导入

BotMRR 是一个 Markdown 文件，两部分缺一不可：YAML frontmatter（完整包定义）+ Markdown 正文（7 个必需节）。
---
botmrr: 1 ← 版本标记 + 完整包定义（扁平字段）
id: demo-team ← 小写 slug，^[a-z0-9][a-z0-9-]*$
release: 1.1.0 ← 语义化版本
agents: ← 1-200 个
- key: commander ← key 规则 ^[a-z0-9][a-z0-9_-]*$
soul: | ← 块标量，≤24000 字节（SOUL 全文，提炼版）
chiefOfStaff: commander ← 必须是某 agent 的 key
rooms: ← 可选，最多 30（demo-status-board 看板）
routines: ← 可选（error-log-watch 巡检示例）
---
# Demo 团队 ← 正文必须含 7 个节（缺一不可）：
## Activation / ## Mission / ## Outcomes / ## Connections / ## Team / ## Chief of Staff / ## Completion rule
🔒 校验与安全：正文缺 7 必需节报 "missing its X section"；key 唯一且匹配正则；引用完整性（chiefOfStaff / room 成员 / routine agent 必须存在）；权限字段被剥离（approvalMode、autoApprove 等防 privilege smuggling）；cwd / 记忆 / 凭据 / 模型选择一律不过包边界。自检脚本：_validate_botmrr.py。
导入三步：Import / From a folder（项目模式）→ 按适配清单填占位符 + 逐角色设 cwd 和模型 → 开工。版本前提：项目模式需 OMB ≥ 2026-08-21（PR #316）。
⚠️ 版本坑（踩过）：新版 OMB 没有"导出团队"按钮（旧版 Export all bots 已移除，服务端 package-export.ts 有能力但无 UI）→ 制作模板 = 手工编写 BotMRR Markdown；备份 ≠ 移植（.ombbackup 是加密整工作区快照，含对话/凭据，恢复覆盖）；导入副本是干净的（无记忆/历史/授权，需重设 cwd 和模型）。

6从零搭建：8 步操作指南（给别人照着做）

每步给出"做什么 + 可复制的骨架"，Demo 实值作示例。
0

前置检查

git --version · java -version（Java 21）· mvn -version（3.9+）· node -v; npm -v（Node 18+）· 可选 MySQL 8.0（自动化测试用 H2 内存库，不依赖 MySQL）
1

初始化仓库结构

git init + 建目录：.agents/skills、.agents/product-workflow-suite、协作机制、文档/机制与方案、文档/团队模板、文档/工程指南、文档/OMB学习笔记、切片、.scratch、backend、frontend
2

写 AGENTS.md（项目级规范）

填：项目定位、流程纪律（SDD 链 + 状态机 + 产物命名）、构建验证命令、领域规则、安全边界。这是所有角色行为的锚点
3

放置技能库

Matt skills 从公开仓库拉取 / 拷贝 .agents/skills/；海天套件走内部渠道拷贝；确认每目录含 SKILL.md，套件内 AGENTS.md / CONTEXT.md / workflow-manifest.json 保持完整
4

写 SOUL → 提炼模板 → 校验

按 6 板块写 SOUL（定位 / 流程门禁 / 分级 / 委派纪律 / 安全边界 / 入口归一）→ 三层分离提炼 → 组装 BotMRR（frontmatter + 7 必需节）→ 用自检脚本验证通过 → 写协作机制/README.md（原适配清单）
5

导入 OMB 团队

桌面端 Teams → Import / From a folder → 逐角色设 cwd 与模型 → 按协作机制/README.md 填占位符 → 检查 routine 默认 paused
5.1

配置分区公共规则（Section Context，趋同双保险之一）

桌面应用左侧边栏「团队地图」→ 分区卡片右上角 Context 按钮 → 粘贴公共规则正文（留档 协作机制/demo-team-section-context.md 的「==== 粘贴区 ====」之间内容）→ Save。只有用户能写（agent 禁写）。即使不配置，各角色 SOUL 已内置【⑥ 入口归一】——双保险删一仍留一
6

搭种子项目（可选）

任何能构建的最小项目即可（Demo 用工单系统：backend Java 21 + Spring Boot + H2 测试 + MySQL 本地；frontend Vue 3 + Vite + TS）
7

验证闭环

跑一个真实需求（建议 M 级）走完整流水线；对照 .workflow-state.json 确认状态流转；闭环后把沉淀固化回适配清单/模板

7安全与凭据边界 · 踩坑清单

/.local-credentials.env 为禁读边界（所有角色不得打开/读取/搜索/索引/摘要，只允许元数据检查）；凭据外置注入（application.yml config import optional:file:...env[.properties]，占位符无默认值、缺失即 fail fast）；部署默认 dry-run（不索要/保存/输出密码、不用 sshpass、双重批准）。
#坑解法
1.env 扩展名不被 Spring 识别，optional import 静默吞错import: optional:file:...env[.properties] 显式格式提示；占位符无默认值 → fail fast
2新版 OMB 找不到"导出团队"按钮没有 UI；用手工 BotMRR Markdown 或 API；.ombbackup 是备份不是模板
3团队包不携带 cwd / 模型 / 记忆 / 凭据导入后逐角色重设 cwd 与模型（特性：模板纯净）
4团队包 skills ≤ 20 个、只带 markdown项目技能库走 cwd 直读，不内联
5项目模式导入需要 OMB ≥ 2026-08-21（PR #316）看 UI 有没有 From a folder tab
6routine 导入后处于启用状态的风险BotMRR 强制 enabledAfterInstall: false，导入后一律 paused
7角色自写 Reviewed 破坏门禁SOUL 明示 Reviewed 只能指挥官写；AI 只写 Draft/Blocked/Not Applicable
8对抗审查用写稿会话的上下文CodeReview 必须以 fresh 上下文审查方案文档
9把构建成功当测试成功 / 只看退出码验证必须检查真实 PASS/FAIL 输出；QA Gate Function 只认本轮新鲜证据
10看板刷屏只广播真正的项目需求状态行；文档/对话/咨询型任务不推
