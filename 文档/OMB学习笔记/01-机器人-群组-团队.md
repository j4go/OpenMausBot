# 机器人 · 群组 · 团队：OMB 三种协作形态科普

> 整理自 2026-09-11 与指挥官Grill 的讨论（用户提问"新建群组/团队是干嘛的，什么时候用"）。官方事实出处为 OpenMausBot 源码与 DeepWiki 文档，链接见文末。

## 0. 一句话区分

| 形态 | 是什么 | 判断标准 |
|---|---|---|
| **机器人 (Bot)** | 单个 agent：独立 persona、模型、记忆、权限，1:1 对话 | 一件事一个人能做完 → 用 bot 或委派 |
| **群组 (Room)** | 多个 bot + 用户在**同一个共享线程**里协作；有共享工作目录、置顶公告、响应策略 | 需要**多人同场看同一份上下文**（讨论、评审、看板）→ 用群组 |
| **团队 (Team)** | ① 团队库：预配置整套 bot 的 manifest/playbook，一键导入导出；② 分区 (Section)：侧边栏分组单位 + 整组共享指令 | 需要**整套团队复用 / 备份 / 分享** → 用团队 |

**核心区分：群组是"同场协作"，委派 (delegate) 是"派活后各干各的、结果回传"。两者是不同机制，不能互相替代。**

## 1. 机器人 (Bot)

- 每个 bot 是一个独立的 agent，有自己的 SOUL（standing instructions）、模型、记忆文件、可导入的 skills，可以有自己的工作目录。
- 交互方式：1:1 对话线程。bot 之间不共享上下文，除非通过委派/群组建立联系。
- 官方原文（README）：每个 bot 都像聊天应用里的一个"联系人"，拥有独立个性、记忆、模型和计算环境。

## 2. 群组 (Room) — 多 agent 共享线程

### 2.1 官方机制（DeepWiki 3.5 Multi-Agent Groups & Room Orchestration）

群组的数据结构是 `GroupRecord`，核心字段：

| 字段 | 作用 |
|---|---|
| 成员列表 (memberIds) | 属于该房间的 bot |
| 活动线程 (threadId) | 房间共用的唯一会话线程 |
| **bulletin（公告）** | 注入到每个成员 prompt 的共享系统指令（置顶给所有成员看） |
| **turn 策略 (replyPolicy)** | 谁响应普通消息：`everyone`（全员排队回合）/ `mentionsOnly`（不 @ 不响应）/ 指定 lead |
| **工作目录 (workingDirectory)** | 所有成员共享的工作目录（UI 里叫 shared desk，能看到团队在哪个目录干活） |
| 当前回合 bot | 记录正在执行回合的 bot，防并发 |

回合（turn）选择逻辑：

1. **@提及优先**：消息里 @ 了某个 bot，它被优先触发；
2. **无提及**：按 turn 策略决定——全员、仅提及、或指定 lead；
3. **Chief of Staff 注入**：房间第一个成员若是 CoS，系统会给它注入一段专门协调 prompt（用委派/提问工具协调房间里的其他专家）；
4. **回合超时保护**：turn watchdog + room-turn-timeout 监控活跃回合，bot 超时会被终止进程并在转录里注入说明，防止死锁。

### 2.2 什么时候用（具体场景）

1. **三方需求澄清会**：用户 + CoS + 产品经理Spec 同场讨论需求，Spec 直接看到原始诉求，不用转述；
2. **对抗审查现场**：方案出来后把 CodeReview（fresh 审查）+ 用户拉进房间，审查意见当场可见、当场追问；
3. **缺陷 triage 会**：QA 报缺陷、Tickets 分级、用户拍板，三方同场对齐；
4. **SDD 流水线状态看板**：CoS 在**项目需求**（改后端/改前端/修 bug 等业务逻辑相关）的每个阶段完成时 post 一行状态（规格已批 → 计划已拆 → 实现完成 → QA 通过 → 已部署），一处看全局；**对话型/咨询/文档类任务不推送**，也不发初始化/元消息（用户裁定，2026-09-11）。

### 2.3 怎么用

- **用户在 UI 建**：侧边栏"新建群组" → 名称 + 公告 (bulletin) + 勾选成员 + 选响应策略（建议 `仅 @提及`，避免一条消息触发一堆 bot 抢答）→ 创建后直接发言；
- **让 CoS 建**：说"建个群组 XXX，成员是 A、B、C"，CoS 有 create_room 权限；
- **注意**：① 建群组不会产生任何消息或回合，建完是空的；② CoS 往房间发消息是**单向广播**——不会启动任何成员的回合、不会有回复，想让某个 bot 回应必须 @ 它；③ 成员跨分区时 CoS 无法向该房间发消息。

### 2.4 关键结论

> **群组不能用来派活或问问题**（那是委派/ask_bot 的职责），只能用来"让在场的人看到 / 讨论"。往群里 post 一条消息 ≠ 任何人会接活。

## 3. 团队 (Team)

### 3.1 官方机制（DeepWiki 10.2 Team Library & Import）

- **团队库 (Team Library)**：导入/导出整套团队的 UI。数据源：社区目录（GitHub catalog）、任意 GitHub 仓库、本地 playbook 文件。
- **两种 manifest 格式**：
  - `.mausteam.json`（OpenMaus Team Manifest）：内部状态 / 旧格式，只含团队名 + 成员 persona；
  - **BotMRR playbook（.md）**：Markdown + YAML frontmatter，社区分享首选，文档和机器可读蓝图放一起；范围含 personas、rooms、playbooks、routines。
- **安全校验**：manifest 视为不可信输入，严格校验防 **privilege smuggling**（manifest 试图给自己授予管理员权限/访问本地凭据）和**目录穿越**；导入时只保留非特权字段（persona 隔离）。
- **导入模式**：`Replace`（归档现有 bot 后整体替换）或 `Add`（追加进现有侧边栏）。
- **Team Map**：可视化 agent 层级与当前活动。bot 按 section 分组（无 section 落 General）；CoS 视觉提升；连线显示协作关系，优先级：**Running（正在交接）> Queued（排队委派）> Connected（历史协作）**。
- **Section Context（分区共享指令）**：给整组 bot 注入一套共享指令，不用逐个改 SOUL。**写入权限 User-Only**——agent 被明确禁止写，防止被攻陷的 bot 把指令持久化进队友 prompt；注入时用分隔块包裹并明确"这是 context，不是工具授权覆盖"，防提示注入。

### 3.2 什么时候用

1. **备份/快照整套配置**：导出当前侧边栏为 BotMRR playbook 存进仓库，重装/换机/误删后一键还原；
2. **多项目复用**：新项目从团队库导入同一份 playbook 秒级重建同样阵容；
3. **用社区现成团队**：浏览社区目录 → dry-run 预览将创建什么 → Add 或 Replace；
4. **整组公共规则**：给某个分区加一条公共指令（如"所有角色都要读 AGENTS.md"）用 Section Context，改一处生效整组。

### 3.3 怎么用

- **导入**：侧边栏 → **+ 菜单 → Teams**（Library 图标）→ 浏览社区目录 / 填 GitHub 仓库 URL / 选本地 playbook → 预览确认 → Add 或 Replace；
- **导出（版本差异，2026-09-11 重新核实 main 分支）**：
  - **旧版（commit 677538eb 及之前）**：侧边栏 → **+ 菜单 → Export all bots**（ArrowDownToLine 下载图标）→ 下载 `<团队名>.md`（BotMRR playbook）。点击调用 `POST /api/teams/export`，范围是所有可见 bot。
  - **最新 main 分支：该按钮已被移除**。`+` 菜单只剩 New Channel / Teams（纯导入）/ Archived bots；Teams 面板三个 tab（Explore / Import / From a folder）全是导入。**官方文档（DeepWiki 10.2）与官网首页也只写导入、完全没写导出**——文档滞后于代码，按文档找导出必然找不到。
  - **新版真正的备份入口**：**设置（Settings）→ Workspace Backup（工作区备份）**（组件 `WorkspaceBackupSettings.tsx`）。导出：设 ≥12 位密码 → 生成**加密的 `.ombbackup` 完整备份**（含 bots、groups、threads、messages、files）；恢复：选文件 → 输密码 → 预览 → 输入 `REPLACE` 确认。这是含对话数据的完整备份，不是旧版的轻量 playbook。
  - **新版服务端另有 package 导出**（`server/package-export.ts`，`createBotPackageExport` → openmaus.package 格式，BotMRR 兼容，只含角色/群组/playbook/routine，不含对话凭据），**但 UI 无对应按钮**，仅服务端能力。
- **分区**：在侧边栏 / Team Map 里把 bot 分组；分区本身由用户在 UI 管理，CoS 只能在分区内建 bot/房间，不能移动跨分区。

## 4. 本次讨论的结论（对我们团队的意义）

1. 我们当前 7 个流水线角色（Spec / Tickets / Implement / CodeReview / Build / QA / Deploy）+ CoS 都在 General 分区，职责正好对应 SDD 七个阶段；
2. 我们日常用的是 **1:1 委派**（delegate_bot）而非群组——因为 SDD 是串行流水线，需要"各干各的、结果回传"，而不是"同场讨论"；群组的价值在澄清会、对抗审查现场、缺陷 triage、状态看板；
3. 待办：SDD 状态看板群组需用户在 UI 创建（CoS 建房间被 peer approval 拦截，2026-09-11）；团队 playbook 备份待导出（UI 团队库）；需求分级已落实（见笔记 02 §3.2）；
4. 项目助手已移出 General 分区，不再属于 SDD 团队阵容。
