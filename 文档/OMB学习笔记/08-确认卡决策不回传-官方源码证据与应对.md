# 08 · 确认卡决策不回传 agent 会话（官方源码证据与应对）

> 调研日期：2026-09-13 · 调研人：Demo-指挥官 · 定性：**OMB 官方设计，非用户操作问题；平台内部行为不一致（team-setup 例外）**
> 源码基线：GitHub `milind-soni/OpenMausBot` main 分支（clone 核实）+ 本机桌面应用 0.1.76 编译产物（`resources\server`）双验证一致。

## 一、问题现象（用户长期困扰）

- 弹确认卡 → 用户点「同意」→ 卡片关闭、decisions.ndjson 记录 user-approved → 但 agent **不自动继续**，仍显示等待用户消息。
- 用户感受：「我每次都点同意，你却说我没回复」；实际是点击决策**从未作为消息回传 agent 会话**，agent 收不到任何信号。

## 二、根因：OMB 的 agent 只有「收到新消息 → 启动新 turn」才运行

OMB 中 agent 只在收到新消息/新 turn 时运行。卡片分两类，机制完全不同：

### ① 问题/权限卡片（ask_user_question、工具审批）——回答回传 ✅
- agent 的 turn **仍在运行**（ask 挂起在 turn 内等待）。
- 用户回答 → `POST /api/bots/:id/respond` → `answerRequest`（`server/index.ts:2924` 附近）→ driver 把回答注入**正在运行的 turn** → agent 继续执行。
- 这就是「问题卡片回答回传会话、交互无断层」的原理。

### ② 确认卡（propose_profile / propose_routine / skill_manage）——点击不回传 ❌
- 工具返回明确指示 agent：「卡片已显示，**结束 turn 等待**」（`server/drivers/agents-proxy.ts:895-900`）。
- 用户确认后服务端只做三件事：**应用变更 + 写 decisions.ndjson + 广播 UI 更新**，然后返回 HTTP 200：
  - `resolveAndSendProfile`（`server/index.ts:6413-6444`，propose_profile 链路）
  - `resolveAndSendRoutine`（`server/index.ts:6388-6411`，propose_routine 链路）
  - skill 确认卡处理（`server/index.ts:8200-8294`，skill_manage 链路）
- **三处均无任何 startTurn / 唤醒 agent 的代码**。
- `decisions.ndjson` 是**审计日志，不是回传通道**：`server/decision-log.ts:16` 注释原文 "fire-and-forget — an audit log must never take down the decision it is auditing"。靠读它确认「用户已批」是 workaround，不是官方支持的回传机制。

### ③ 关键不一致：propose_team_setup / propose_bot_deletion 确认卡有唤醒 ✅
- 用户确认后 → `resolveAndSendTeamSetup`（`server/index.ts:6291-6295`）→ `dispatchTeamSetupResume`（`6257-6270`）→ `startTurn(botId, "…team setup decision …: Report this exact result and continue the user's already requested work", { cardContinuation: true })`——**真的唤醒 agent 并注入结构化结果**。
- 因此官方工具描述中 team-setup 写「the decision and structured result **resume you automatically once**」，而 propose_profile 只写「End this turn and wait」。
- **同一平台、两类设计**，这是平台内部不一致，非文档口径问题。

## 三、版本核实

- 本机桌面应用 0.1.76 的编译产物（`resources\server` 下）与 main 分支实现一致：`cardContinuation` 共 19 处（仅 team-setup / bot-deletion 链路使用），profile-requests.js 中无任何 wake/startTurn 调用。
- GitHub issue 检索未发现该问题的既有报告。

## 四、为什么「修复过还是存在」（2026-09-13 复盘）

- 上次（09-13）的修复是**流程规避**：改用 ask_user_question 问题卡片直问 + 主动读 decisions.ndjson 核对 + 提醒用户「点完回一句」。
- 规避有效但**根除不了**：SOUL / 团队配置类变更**只能走确认卡**（平台强制），这类卡片点击后官方就是不回传，每次弹卡后仍需用户发消息才能唤醒 agent。

## 五、应对流程（团队固化，2026-09-13 用户批准）

1. **发确认卡时**（propose_profile / propose_routine / skill_manage）：随卡明确告知需求方「**点完请回一句（任意字）**」，避免对方以为点卡即完成。
2. **被唤醒后**：先读 `~/.openmausbot/decisions.ndjson` 核对 user-approved 记录，再执行下一步，不凭会话内无回复判定未批。
3. **表述纪律**：不用「你没回复」归因用户，改说「**我没收到回传信号**」——诚实归因于平台机制。
4. **日常审批优先问题卡片**（ask_user_question 二选一）：回答回传会话、无断层；确认卡留给 SOUL / 团队配置类等平台强制的场景。
5. **上游方向**：建议官方将 propose_profile / propose_routine / skill_manage 对齐 team-setup 的 `cardContinuation` 唤醒模式（本文源码证据可直接引用）；是否提 issue 由需求方决定（2026-09-13 用户裁定暂不提）。
