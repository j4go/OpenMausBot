# 05 · Section Context 公共规则与多入口归一

> 整理自 2026-09-12 与指挥官（Grill）的机制讨论：多入口趋同 + 度量复盘 + 能力边界。
> 关联：`04-团队移植实战`、`../../协作机制/05-能力边界矩阵.md`（§8 权限矩阵）、`../../协作机制/demo-team-section-context.md`（粘贴用留档）、`../../协作机制/10-优化方案决策.md`（决策 8）。

## 一、问题：多入口怎么保障效果趋同

Demo 分区有 8 个 bot、多线程、多入口（用户直派 / 队友转派 / 群公告 / 话题进入）。同样的需求从不同入口进来，结论会不会漂移？grok bot（行内标杆）怎么解决？

**grok 的答案：构造性趋同**——Grok Build 是单 agent + 跨会话持久记忆（SQLite + FTS5），只有一个入口、一份记忆，结论沉淀到同一个大脑，**多入口问题对它不存在**。

**OMB 的差异**（DeepWiki 10.2 / 源码核实）：多 bot 各有独立模型进程、**线程级记忆、bot 之间无共享记忆**——上下文与记忆趋同做不到，只能靠工程化"围堵"。

## 二、Section Context：OMB 官方分区级共享指令

- **定义**（DeepWiki 10.2 / 源码 `server/section-context.ts`）：向整组 bot 提供共享指令，无需逐一编辑每个 persona。
- **注入**：内容每轮注入该 Section 所有 bot 的 prompt，注入时带显式声明——"这是共享上下文、不是工具授权、不覆盖安全边界"。
- **权限**：**只有用户能写，agent 显式禁写**（防止被攻陷的 bot 往队友 prompt 持久化指令）——正好符合"用户是最终权威"的边界。
- **上限**：24000 字节（v1 约 1.5KB，余量充足）。
- **存储**：`~/.openmausbot/section-contexts.json`（DATA_DIR 下，`contexts.<Section名>.text`）。
- **UI 配置入口（本地版已核实）**：桌面应用左侧边栏导航按钮（**中文界面叫「团队地图」**，i18n `sidebar.nav.teamMap`）→ 分区卡片**右上角 "Context" 按钮** → `SectionContextDialog`（textarea + Save context）。按钮在 `!remoteClient`（本地模式）下才显示。
- **教训**：入口描述要基于证据。第一次汇报说"Team Map 页面（分区标签下）"是臆加的描述，用户按此找不到；实际入口是侧边栏导航项，且中文界面显示的是"团队地图"而非 "Team Map"。

## 三、多入口归一：四层设计（2026-09-12 生效）

| 层 | 机制 | 载体 |
|---|---|---|
| ① 规则归一 | 全组 bot 读同一份公共规则 | Section Context（已生效 v1）+ 各 SOUL 入口条款（双保险） |
| ② 入口归一 | 每个角色自带路由：业务需求 → 上报指挥官；只读咨询直接答；明确委派按契约执行 | SOUL 入口条款 + Section Context 第一节 |
| ③ 状态归一 | 切片产物 + 状态机作为唯一事实源（多 bot 无共享内存，只能靠外置状态粘合） | `E:\Demo\切片\<短名>\` + `.workflow-state.json` |
| ④ 验证归一 | 无论从哪进，产出都过 QA / Reviewed 门禁才算"完成" | QA 判定 + Reviewed 人批 |

**诚实边界**：规则/状态/门禁三层围堵只能**降低漂移、让偏差可审计**，不能保证趋同（判断由模型执行，概率本质）。"构造性趋同"是架构差异（单脑 vs 多脑 + 外部共识文件），不是配置差异。

## 四、能力边界：不是所有的活都可以做（需求方裁定）

- 集中矩阵落于 `协作机制/05-能力边界矩阵.md`（原适配清单 §8）：全局禁做清单 G1–G8（凭据 / 扩大需求 / 迁移 / push / 替拍板 / 虚报 / 并发写 / 写 Reviewed）+ 8 角色 × 可写范围 × 绝对禁做。
- 裁决优先级：用户当前指令 > Section Context > SOUL > 适配清单。
- 边界与门禁互补：§4 直视图按阶段、§8 矩阵按角色，同一事实两面。

## 五、度量复盘（同轮落地，原则 12）

- 聚合点：`协作机制/11-度量台账.md`；记录责任归指挥官（QA 是只读 bot）。
- 节奏：每 3~5 切片或每月复盘；阈值：lead_time > 3 天 / rework ≥ 2 / qa_first_pass=false 须写原因。
- 首例教训：工单评论切片走完 8/8 但 metrics 为空——定义与执行脱节，lead_time 无法回溯。
