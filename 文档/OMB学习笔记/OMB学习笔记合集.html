OpenMausBot 机制科普系列，整理自 2026-09-11 与指挥官 Grill 的讨论；官方事实出处为 OpenMausBot 源码与 DeepWiki。分享同事用。

01机器人 · 群组 · 团队：三种协作形态

一句话区分：群组是"同场协作"，委派是"派活后各干各的、结果回传"——两者是不同机制，不能互相替代。

🤖 机器人 (Bot)

单个 agent：独立 persona、模型、记忆、权限，1:1 对话
  • 有独立 SOUL、模型、记忆文件、可导入 skills、自己的工作目录
  • bot 之间不共享上下文，除非通过委派/群组建立联系

👥 群组 (Room)

多个 bot + 用户在同一个共享线程里协作
  • 共享工作目录、置顶公告（bulletin）、响应策略（everyone / mentionsOnly / lead）
  • 回合选择：@提及优先 → 无提及按 turn 策略 → CoS 注入协调 prompt → 超时保护
  • 不能用来派活或问问题（那是委派/ask_bot 的职责）；post 一条消息 ≠ 任何人会接活

🏢 团队 (Team)

团队库：预配置整套 bot 的 manifest/playbook，一键导入导出
  • BotMRR playbook（.md）：Markdown + YAML frontmatter，社区分享首选
  • 安全校验防 privilege smuggling 和目录穿越；导入只保留非特权字段
  • Section Context：给整组 bot 注入共享指令，写入权限 User-Only

什么时候用什么（具体场景）

场景用哪个说明
三方需求澄清会 / 对抗审查现场 / 缺陷 triage群组需要多人同场看同一份上下文；审查意见当场可见、当场追问
SDD 流水线状态看板群组CoS 只在项目需求（业务逻辑相关）各阶段完成时 post 一行状态；对话型/咨询/文档类不推送，不发初始化/元消息（用户裁定 2026-09-11）
1:1 派活 / 问问题委派 / askSDD 是串行流水线，需要"各干各的、结果回传"而不是"同场讨论"
备份/快照整套配置 / 多项目复用 / 社区现成团队团队导出 BotMRR playbook 存仓库；新项目一键还原
⚠️ 群组注意事项：建群组不会产生任何消息或回合；CoS 往房间发消息是单向广播（不会启动任何成员的回合），想让某个 bot 回应必须 @ 它；成员跨分区时 CoS 无法向该房间发消息。建议响应策略用"仅 @提及"，避免一条消息触发一堆 bot 抢答。
📎 结论（对我们团队的意义）：7 个流水线角色 + CoS 在 General 分区，职责正好对应 SDD 七个阶段；日常用 1:1 委派而非群组；待办：状态看板群组需用户在 UI 创建（CoS 建房间被 peer approval 拦截）、团队 playbook 备份。

02指挥官如何派活：委派机制与需求分级

核心：OMB 里 bot 间通信全部经过 Agents Proxy 中间层（注入每个 bot 进程的 MCP 服务器），强制三件事：递归限制（防无限链式委派）、权限（peer approval）、用户可见性（全程可审计）。
list_bots 查
列出同分区 bot 及状态——派活前先确认名册
ask_bot 同步
同步咨询：等对方回完才继续——只需要一句 inline 答复的短问题
delegate_bot 异步
异步派活：立即返回，对方回合结束后结果自动回传——SDD 各阶段派活的主通道
create_bot / propose_routine Chief
建 bot / 提议定时任务（Chief 专属）

委派生命周期与安全护栏

环节机制
生命周期Queueing（校验目标存在 + 委派深度允许）→ Persistence（落盘，进程重启不丢）→ Draining（回合结束时触发下一个）→ Approval（源 bot 开启审批时挂起直到 UI 卡片批准）
Peer approvalbot 间通信默认可配置为需要你的卡片批准（Allow / Deny / Always allow，可白名单）；15 分钟不响应自动拒绝
递归保护委派深度上限当前为 1——被委派的 bot 不再带通信集成，链式委派到此为止
可见性每次 bot↔bot 交流都镜像到共享频道，双方 1:1 线程里都有活动标记

🔒 三条铁律：① 一次只允许一个写入角色碰仓库（防并发写冲突）；② Reviewed 只能人写（AI 只写 Draft/Blocked/Not Applicable）；③ 部署默认 dry-run（无 runbook + 本轮明确批准时不真部署）。诚实边界：这套编排不是绝对确定的工作流引擎——skill 选择和委派仍由模型执行，靠"明确角色边界 + 输入/输出/写入范围 + 持久化中间产物 + 独立 Review + 真实命令输出 + 人批门禁"降低漂移。

需求分级 L / M / S（解决"小需求过重"）

级别典型需求流程门禁
L 大型/从 0新功能、跨层改动完整流水线：澄清 → Spec → 计划 → 对抗审查 → Reviewed → TDD → Review → Build → QA → Deploy全部门禁，一个不少
M 中型/单层模块内增强、bug 修复澄清 →（轻量计划）→ 对抗审查 → Reviewed → TDD → Review → QA保留人批 + QA，可简化或跳过正式 proposal
S 小型/快速文案、样式、单点修复直接委派 Implement → Build / QA 快速验证至少过 Build + QA 快速判定；跳过对抗审查

绕过指挥官直接给节点 bot 派活：会失去什么

失去说明
① 串行化同时派两个写入 bot 可能同时改仓库 → 冲突
② Reviewed 人批门禁绕过 = 没有"人批放行"环节
③ QA 门禁没有 wrap-up 验证判定，缺陷可能直接流到部署
④ 全局上下文节点 bot 单线程看不到澄清记录、ADR、上游基线、并行需求状态
✔ 什么时候推荐绕过：只读咨询（"这个 API 怎么调"）→ 直接 ask_bot，快；明确要"快速小改、接受风险"→ 可绕过但建议事后补 QA 判定。必须走指挥官：涉及写仓库、多角色协作、需要门禁。业界对照：我们的机制符合 Spec-first / TDD / four-eyes / CI 门禁 / 状态机 / ADR 主干，且是 Matt 方法链的完整适配；有意差异 = 把 review 从 implement 中拆出（独立 CodeReview，有公开依据）。

03团队模板 BotMRR：制作、导出与跨项目移植

一句话结论：换项目不用重建团队——把当前团队提炼成"与项目解耦"的 BotMRR 模板（.md，随仓库版本化），新项目 Import 副本、重设 cwd 即可。核心机制：bot 定义全局存储（~/.openmausbot/bots.json + SOUL.md），cwd 只是一个指针字段。

三个可选做法对比

方案做法适合代价
A. 团队模板 + 导入（推荐）团队固化成 BotMRR .md 存仓库 → 新项目 Import（或 From a folder 项目模式）→ 重设 cwd多项目并行、每项目要独立记忆/历史一次性模板成本；导入后重设 cwd/模型
B. 同一团队切 cwd团队就一套，换项目时改 8 个 bot 的 working folder同一时间只做一个项目记忆/历史全局混在一起，项目间会串；无法并行
C. From a folder（scout）选新目录 → OMB 自动分析并提议团队从零的新项目提议的是它生成的团队，不是你的模板

导出路径的版本坑（务必记住）

版本导出入口现状
旧版（commit 677538eb 及之前）侧边栏 + 菜单 → Export all bots（下载 BotMRR .md）已移除
新版（当前 main）+ 菜单只剩 New Channel / Teams（纯导入）/ Archived bots没有导出按钮
官方文档（DeepWiki 10.2）+ 官网只写导入，没写导出文档滞后于代码
⚠️ 备份 ≠ 移植：Settings → Workspace Backup 导出的是加密 .ombbackup（整工作区快照，含对话/凭据，恢复覆盖），是备份不是团队模板。服务端 package-export.ts 有团队级导出能力（纯定义、不含 cwd/记忆/凭据），但无 UI 按钮 → 制作模板 = 手工编写 BotMRR Markdown。

三层分离提炼法（模板必须与项目解耦）

~60%

① 通用核心

  • SDD 流程骨架、状态机约定、单一写入者、Gate Function、TDD、缺陷 triage
  • 原样保留
~25%

② 项目规范

  • AGENTS.md 引用、切片路径、schema-first、skill 引用
  • 改占位符（{{PROJECT_NAME}} 等），实值外置到适配清单
~15%

③ 机器/环境硬编码

  • E:\ 路径、.bat 脚本、内网地址、tag 格式、凭据文件路径
  • 全部删除，只保留"见 {{ADAPT_FILE}}"式引用
⭐ 判断标准：模板里不允许出现任何"这台机器 / 这个仓库"才有的字符串。BotMRR 结构：YAML frontmatter（botmrr: 1 / id / release / agents / chiefOfStaff / rooms / routines）+ 正文 7 必需节（Activation / Mission / Outcomes / Connections / Team / Chief of Staff / Completion rule）。校验规则（zod 严格）：key 唯一且匹配正则；引用完整性；soul ≤ 24000 字节；颜色限 10 枚举色；权限字段被剥离（防 privilege smuggling）。导入副本是干净的：无记忆/历史/授权，需重设 cwd 和模型；routine 强制 enabledAfterInstall: false（默认 paused）。

04团队移植实战：E:\Demo 工作区与 Skill 导入机制

场景：把 OpenMetadata 的 SDD 团队移植到 E:\Demo（脱离 OpenMetadata，改用 Matt 工程 skills + 海天 product-workflow-suite）。结论：团队模板 + 项目技能库分离；skill 进 OMB 有三条通道，最佳实践是 cwd 直读而非导入。

Skill 进入 OMB 的三条通道（源码核实）

通道 1团队包内联

  • BotMRR package.skills.entries（完整 SKILL.md 文本）
  • ≤20 个/包；每 ≤256KB；source 拒绝绝对路径
  • 导入后默认 disabled，review 后启用

通道 2GitHub 导入

  • bot 设置页 Import，只接受 owner/repo、github.com URL、raw SKILL.md
  • 每包 ≤30；仅 markdown
  • UI 不接受本地路径（parseSkillSource 对非 GitHub "loudly refused"）

通道 3skill_manage 创建

  • 指挥官工具 → 用户批准卡
  • → workspace skills → bot imported skills
  • 沉淀 OMB 级通用纪律
✅ E:\Demo 落地决策：49 个 skills（Matt 30 + 海天 19）超 20 上限，且海天套件依赖非 md 资源（scripts/、agents/openai.yaml、migrate_suite.mjs），团队包只带 markdown 会破坏 → 项目技能库不进 OMB，靠 cwd 直读（bot 的 cwd 指向 E:\Demo，文件工具直接读 .agents/）；模板 SOUL 只写"技能取用规则 + 映射表位置"；映射表放适配清单 §3。流程统一口径：产物命名用海天（clarify.md / prd.md / …），门禁用 SDD（Reviewed 人批、QA 判定）——两套状态机同构（Draft/Reviewed/Blocked/Not Applicable），不搞两套流程打架。
📣 看板广播边界（用户裁定 2026-09-11，同步固化）：状态看板只广播真正的项目需求（改后端/改前端/修 bug 等业务逻辑任务）的阶段状态；对话型/文档型/咨询型任务一律不推，不发初始化/元消息；看板消息必须是需求状态行。

05Section Context 公共规则与多入口归一（2026-09-12）

问题：OMB 多 bot 各自独立模型进程、无共享记忆，「多入口怎么保证效果趋同」做不到 Grok Build 那种构造性趋同（单脑 + 跨会话持久记忆），只能工程化"围堵"。方案：OMB 官方分区级共享指令（Section Context）公共规则 + 各 SOUL 入口归一条款双保险 + 四层设计。

Section Context 官方机制（源码核实）

  • 用途：给整组 bot 注入共享指令，不用逐个改 SOUL；内容每轮注入该分区所有 bot 的 prompt，带显式声明（共享上下文 ≠ 工具授权 / 安全边界覆盖）
  • 写入权限 User-Only：只有用户能写，agent 显式禁写（防被攻陷的 bot 往队友 prompt 持久化指令）；上限 24000 字节
  • 配置入口：桌面应用左侧边栏「团队地图」（Team map）→ 分区卡片右上角 Context 按钮 → 粘贴正文 → Save；存储于 ~/.openmausbot/section-contexts.json
  • Demo v1 已生效（2026-09-12，用户粘贴）：入口归一 + 四条铁律 + 事实源指针 + 协作姿态；留档 协作机制/demo-team-section-context.md（v2 待用户重新粘贴）

多入口归一：四层设计

层机制载体
① 规则归一全组 bot 读同一份公共规则Section Context（已生效 v1）+ 各 SOUL 入口条款（双保险）
② 入口归一每角色自带路由：业务需求→上报指挥官；只读咨询直接答；明确委派按契约SOUL 入口条款 + Section Context 第一节
③ 状态层切片 + 状态机唯一事实源切片/.workflow-state.json（Reviewed 唯一写入者=指挥官）
④ 验证层QA 判定 + Reviewed 门禁不可豁免QA-Pending → Passed / Blocked
⚖️ 能力边界矩阵：适配清单 §8——全局禁做 G1–G8（不读凭据 / 不扩大需求 / 不迁移 / 不 push / 不替需求方拍板 / 不虚报 / 不并发写 / 不写 Reviewed）+ 8 角色 × 可写范围 × 绝对禁做 + 裁决优先级（用户当前指令 > Section Context > SOUL > 适配清单）。QA/CodeReview 只读不写仓库；Deploy 无批准只 dry-run。
📏 诚实边界：规则 / 状态 / 门禁三层围堵只能降低漂移、让偏差可审计，不能保证趋同（模型判断概率本质）。「构造性趋同」是架构差异（单脑 vs 多脑 + 外部共识文件），不是配置差异。度量复盘见 协作机制/11-度量台账.md（原则 12：lead_time>3天 / rework≥2 / qa_first_pass=false 须写原因，QA 判定后 24h 内补记，责任归指挥官）。
