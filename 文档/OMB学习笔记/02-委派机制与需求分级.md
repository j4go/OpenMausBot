# 指挥官如何派活：OMB 委派机制与需求分级科普

> 整理自 2026-09-11 与指挥官Grill 的讨论（用户提问："你发需求给我是不是会走完整流程？指派依据是需求轻重吗？能跳过你直接给节点 bot 派活吗？我们符合业界最佳实践吗？"）。
> 官方机制出处为 OpenMausBot 源码与 DeepWiki 4.6；项目侧机制出处为 `文档/流程与机制/OpenMausBot-SDD-Agent-Setup.md`，链接见文末。

## 0. 三个问题的一句话回答

| 问题 | 一句话回答 |
|---|---|
| 发需求给我，你会走完整流程吗？ | 不会"我一个人全干"，也不是"看心情指派"——我是**流程控制器**：按固定流水线逐阶段委派给对应角色，关键门禁由人控制。这是机制，不是个人选择。 |
| 指派依据是需求轻重吗？ | 目前**不是**——默认所有需求走同一条完整流水线（这正是小需求过重的根源）；按需求轻重分级（大需求 / 快速迭代小需求）是下一步可以显式化的优化。 |
| 能跳过你直接给节点 bot 派活吗？ | **技术上可以**（bot 是你的），但会失去串行化、人批门禁、QA 门禁和全局上下文；只适合只读咨询或你明确要"快速小改且接受风险"。 |

## 1. 官方机制：OMB 的委派是怎么实现的（DeepWiki 4.6）

**科普**：OMB 里 bot 之间的通信不是"直接打电话"，而是全部经过一个叫 **Agents Proxy** 的中间层——一个注入到每个 bot 进程的 MCP 服务器，所有 bot↔bot 交互都回经 harness，强制三件事：**递归限制**（防止无限链式委派）、**权限**（peer approval）、**用户可见性**（comms visibility）。

### 1.1 四个委派工具

| 工具 | 语义 | 对应我们的用法 |
|---|---|---|
| list_bots | 列出同分区 bot 及状态 | 我派活前先确认名册 |
| ask_bot | **同步**咨询：等对方回完才继续 | 只需要一句 inline 答复的短问题 |
| delegate_bot | **异步**派活：立即返回，对方回合结束后结果自动回传 | SDD 各阶段派活的主通道 |
| create_bot / propose_routine | 建 bot / 提议定时任务（Chief 专属） | 建新角色、安排例行任务 |

关键：`delegate_bot` 是异步交接——我的回合立刻结束，对方稍后启动自己的回合，完成后结果**自动唤醒我**。所以"派活"不等于"等结果"；我派完就向你汇报、继续干别的。

### 1.2 委派生命周期（delegation lifecycle）

1. **Queueing（排队）**：校验目标 bot 存在 + 当前委派深度允许（防无限递归）；
2. **Persistence（持久化）**：待处理委派落盘，进程重启不丢；
3. **Draining（排空）**：bot 回合结束时 harness 触发下一个待处理委派；
4. **Approval（审批）**：源 bot 开启审批时，委派挂起直到你在 UI 点卡片。

### 1.3 安全护栏

- **Peer approval（对等审批）**：bot 间通信默认可配置为需要你的卡片批准（Allow / Deny / Always allow，可白名单指定配对）；**15 分钟不响应自动拒绝**，防止 bot 无限等待。
- **递归保护**：委派深度上限当前为 1——被委派的 bot 不再带通信集成，链式委派到此为止。
- **Comms visibility（可见性）**：每次 bot↔bot 交流都镜像到一个共享频道，双方 1:1 线程里都有活动标记——**全程可审计，你都能看到**。

## 2. 我们这套流水线：指挥官视角的完整机制

### 2.1 流水线与角色映射（Setup 文档 §3）

```text
你发需求
  ↓
指挥官Grill     澄清需求、范围、非目标、验收标准（读 AGENTS/CONTEXT/UPSTREAM_BASELINE/相关 OpenSpec）
  ↓
产品经理Spec    写成 openspec/changes/<change>/proposal.md（问题/目标/非目标/验收标准/风险）
  ↓
技术经理Tickets 拆成小的可验证任务（精确路径、依赖、验证命令、完成定义）
  ↓
代码审查CodeReview  对抗审查（fresh 上下文，三轴 + 人机两句）—— 在你批准之前跑
  ↓
【人写 Reviewed】  状态机唯一人批门禁
  ↓
开发工程师Implement  TDD（RED-GREEN-REFACTOR），一次一个任务
  ↓
代码审查CodeReview  实现后静态双轴审查（Standards + Spec）
  ↓
本地构建Build       起栈 / 构建 / 健康检查
  ↓
QA验证  计划层判定（run-mode 分级）+ wrap-up 验证门禁（Gate Function）→ QA-Passed / QA-Blocked
  ↓
测试服部署Deploy    默认 dry-run；真实部署需 runbook + 本轮明确批准
```

### 2.2 三条铁律

1. **一次只允许一个写入角色**碰 `E:/OpenMetadata`——防止并发写冲突，所以我总是串行委派；
2. **Reviewed 只能人写**：状态机 `.workflow-state.json` 里 AI 只写 `Draft` / `Blocked` / `Not Applicable`，`Reviewed` 只能我（或你）写——写稿的人不能自己放行自己；
3. **部署默认 dry-run**：没有 runbook + 本轮明确批准时，Deploy 只能演练。

### 2.3 必须诚实说明的一点（Setup §1 原文结论）

> 这套编排**不是绝对确定的工作流引擎**。skill 选择和委派仍由模型执行，因此用"明确的角色边界 + 输入/输出/写入范围 + 持久化中间产物 + 独立 Review + 真实命令输出 + 人批门禁"来降低漂移。

翻译：流水线是"强约定"，不是"强执行"——每一步是否发生、怎么发生，依赖我和各角色的遵守程度；门禁和产物是兜底。

## 3. 需求轻重：当前机制与建议分级

### 3.1 当前状态：一律全流程

现在无论需求大小，默认都走完整流水线。这是有意为之的**保守默认**（从 0 的大需求有完整保障），代价是**小需求过重**：改个文案也要过规格 → 计划 → 对抗审查 → TDD → QA → 部署全链。

### 3.2 已落实：显式分级（L / M / S 三条 lane）

| 级别 | 典型需求 | 流程 | 门禁 |
|---|---|---|---|
| **L 大型 / 从 0** | 新功能、跨层改动（Schema + 后端 + 前端 + 迁移） | 完整流水线：澄清 → Spec → 计划 → 对抗审查 → Reviewed → TDD → Review → Build → QA → Deploy | 全部门禁，一个不少 |
| **M 中型 / 单层** | 一个模块内的功能增强、bug 修复 | 澄清 →（轻量计划）→ 对抗审查 → Reviewed → TDD → Review → QA | 保留人批 + QA，可简化或跳过正式 proposal |
| **S 小型 / 快速迭代** | 文案、样式、单点修复 | 直接委派 Implement（或我直接改）→ Build / QA 快速验证 | 至少过 Build + QA 快速判定；跳过对抗审查 |

判定发生在**澄清阶段**，指挥官与需求方对齐"这条需求走哪条 lane"，需求方也可直接指定。**已写入 `文档/流程与机制/OpenMausBot-SDD-Agent-Setup.md` §3.10（2026-09-11 落实）**，指挥官按此执行。

## 4. 跳过指挥官直接给节点 bot 派活

### 4.1 技术上可以

节点 bot 是你的 bot，你直接给它们发消息，会启动它们自己的线程，按它们自己的 SOUL + skills 执行。

### 4.2 直接给各节点 bot 派活：各自会走什么流程

| 你直接发消息给 | 它按自己的 SOUL + skill 会做什么 | 缺什么（相对完整流水线） |
|---|---|---|
| 产品经理Spec | 读 AGENTS.md / 你的原话 → 写 `openspec/changes/<change>/proposal.md` | 没有澄清环节（它只看到你的原话，看不到背景），proposal 可能跑偏；没有 Reviewed 门禁 → 状态机卡在 Draft |
| 技术经理Tickets | 把任务拆成小步（精确路径 / 依赖 / 验证命令 / 完成定义） | 没有 proposal 可拆时只能凭空拆，容易拆错层或漏依赖 |
| 开发工程师Implement | TDD：先写失败测试 → 最小实现 → 重构，跑测试并如实报告 | 没有独立 CodeReview（自己审自己）、没有 QA 门禁，缺陷可能直接漏到部署 |
| 代码审查CodeReview | 只读审查任意 diff（标准 / 规格双轴） | 本身安全；但没有实现产出前没东西可审——它不产生交付物 |
| 本地构建Build | 起栈 / 构建 / 健康检查 | 本身安全；但不了解需求上下文，只能验证"栈能跑"，验证不了"需求对不对" |
| QA验证 | 跑计划层判定 + wrap-up 验证 → QA-Passed / QA-Blocked | 没有验收标准来源时只能自己猜"什么算对"，判定可能失真 |
| 测试服部署Deploy | 默认 dry-run；真实部署要 runbook + 本轮明确批准（双重批准） | 缺批准时永远只演练，不会真部署 |

**共同点**：节点 bot 都是**单线程上下文**——看不到澄清记录、ADR、上游基线、其他并行需求的状态。绕过我 = 失去全局上下文 + Reviewed 人批门禁 + QA 门禁 + 写冲突保护（同一时刻多个写入 bot 同时改 `E:/OpenMetadata`）。

### 4.3 但你会失去四样东西

1. **串行化**：我负责"同一时刻只有一个写入角色碰仓库"。绕过我直接派两个写入 bot，可能同时改 `E:/OpenMetadata` → 冲突；
2. **Reviewed 人批门禁**：状态机里 Reviewed 只能我写。绕过我 = 没有"人批放行"环节；
3. **QA 门禁**：没有 wrap-up 验证判定（QA-Passed / QA-Blocked），缺陷可能直接流到部署；
4. **全局上下文**：澄清记录、ADR、上游基线、当前并行需求的状态——节点 bot 的单线程看不到这些。

### 4.4 什么时候推荐绕过、什么时候必须走我

| 场景 | 建议 |
|---|---|
| 只读咨询（"这个 API 怎么调"、"看看某文件"） | 直接 ask_bot 或私聊节点 bot，快 |
| 明确要"快速小改、接受风险" | 可以绕过，但建议事后让我补 QA 判定 |
| 涉及写仓库、多角色协作、需要门禁 | **必须走我**——这就是我存在的意义 |

## 5. 业界最佳实践对照

### 5.1 我们机制的业界对应物（都是成熟实践的 agent 化）

| 业界实践 | 内容 | 我们的对应 |
|---|---|---|
| **Spec-driven development / OpenSpec**（GitHub Spec Kit 同源） | 先写 proposal（问题/目标/非目标/验收标准）再动手 | 产品经理Spec + `openspec/changes/` |
| **TDD（RED-GREEN-REFACTOR）** | 先写失败测试 → 最小实现 → 绿色重构 | 开发工程师Implement |
| **Four-eyes 审查**（实现者不能审自己） | 独立 reviewer 检查 diff | 代码审查CodeReview（fresh 对抗审查 + 静态双轴） |
| **CI 门禁** | 构建、格式、测试不过不能合入 | 本地构建Build + QA 门禁（run-mode 分级） |
| **状态机 / 审批流** | 关键状态只能由指定角色写入 | Reviewed 只能人写；QA-Pending → Passed / Blocked |
| **ADR（架构决策记录）** | 重大取舍留档、不可逆 | `文档/adr/` |
| **Matt Pocock 方法链**（grill → spec → tickets → implement → review） | 社区流行的 agent 工作流 | Setup §5.1 逐项对照，我们的主链路就是它的适配 |

### 5.2 与通用做法的一个有意差异

Matt 的 `implement` 内部包含 review；我们**拆成实现者 + 独立 CodeReview 两个角色**。理由（Setup §5.1.1）：实现者审查自己刚写的代码容易默认自己正确；Review 只需读权限、可实现最小权限；多模块仓库（Java/Python/React/Schema）独立 Review 更容易发现跨层遗漏。这是有公开依据的架构适配（Matt 仓库有专门 issue 讨论把 review 从 implement 中拆出）。

### 5.3 可优化清单（按性价比排序）

1. ✅ **需求分级显式化**（§3.2 的 L/M/S lane）——已写入 Setup 文档 §3.10（2026-09-11 落实），解决"小需求过重"；
2. **多需求并行**：每个需求开一个我的独立线程，串行委派但多需求可同时推进，让闲置 bot 动起来；
3. **状态看板群组**：我仅在**项目需求**（业务逻辑相关）各阶段完成时广播一行状态，你一处看全局（见笔记 01 §2.2）；对话型任务不推送（用户裁定，2026-09-11）——**建房间需用户在 UI 操作**（CoS 建群组被 peer approval 拦截，2026-09-11）；
4. **团队 playbook 备份**：导出当前 8-bot 配置为 BotMRR 存仓库，防误删 / 换机（见笔记 01 §3.2）；
5. **Section Context**：若给整套流水线加公共规则（如"所有角色必读 AGENTS.md"），用分区共享指令一次生效，不用改 7 个 SOUL。

## 6. 结论

- 我们的机制**符合业界最佳实践的主干**：Spec-first、TDD、独立审查、门禁、状态机、ADR 一应俱全，且是 Matt 方法链的完整适配；
- 主要差距在**流程粒度**：小需求成本偏高（已通过 L/M/S 分级缓解，见 §3.2）；**可见性**待看板群组落地；**并行度**对单人开发无必要，不做；
- 剩余优化：看板群组（需用户在 UI 创建）+ 团队 playbook 备份（UI 导出），均低成本、不需要增加 bot。
